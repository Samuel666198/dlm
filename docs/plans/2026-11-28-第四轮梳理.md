## 1. 视频下载「还是不行」——功能是通的，缺的是「看得见」

### 实测（本机，0.7.7 代码）

| 路径 | 结果 |
|---|---|
| 命令行复刻 GUI 派发的 argv（含 `--quiet` / `--out-name` / `--connections`） | 退出码 0，落点 `BV1atse6EEfx.mp4` **154,175,975 字节** |
| **GUI 全链路**（queue 里一条 `video=true` 的 queued 任务） | `queued → running → done`，落点同样 **154,175,975 字节** |

用的是真 B 站地址，真网络。

### 那为什么看着"不行"

视频任务在界面上**没有任何反馈**：

1. `total_len` 一直是空 —— 队列不知道视频有多大，列表"大小"列显示 `?`
2. `progress` 一直是 0 —— `--quiet` 把 `video::run` 的所有输出都关掉了
   （`src/video.rs:245/299/308/335` 全是 `if !quiet`），所以 GUI 的日志也是空的
3. 于是一条正在下 154 MB 的任务，表现就是"没有大小、没有进度、日志空白"，
   直到突然变 done —— 看起来就像没在动

### 与工作区参考实现的差异（你让我对比的那两个）

| 维度 | 我们（`src/video.rs`） | `video-knowledge-workbench/backend/app/media/remote.py` |
|---|---|---|
| 接入方式 | **起子进程**调 `yt-dlp.exe` | 直接 `import yt_dlp`，Python API |
| 进度 | 只解析 stdout 的 `[download] xx%`，且 `--quiet` 时不输出 | 回调 `progress_hook`，天然有进度/速度/ETA |
| Cookies | 不传（宿主有 cookie，但视频这条没用上） | 用 `requests.Session` 带会话 |
| UA 伪装 | 无 | 有（抖音那条专门伪造） |
| 站点专用解析 | 无（全交给 yt-dlp） | 抖音手写 `RENDER_DATA`/`_ROUTER_DATA` |
| 音视频合并 | 交给 yt-dlp 自己找 ffmpeg | ffmpeg 流水线 |

结论：**差距不在"能不能下"，在"能不能看见"和"登录态站点的成功率"**。

### 建议（分两步）

- **先补可见性**（低价、收益最大）：视频任务不再用 `--quiet` 吞掉输出，
  把 `[download] xx%` 与总长写回队列的 `delivered`/`total_len`，
  这样列表有大小、进度条会动、日志有序言（标题、体积、格式）。
- **再补登录态**：把宿主已有的 cookie 传给 yt-dlp（`--cookies` 临时文件或
  `--add-header`），这是 B 站高清、抖音、小红书能不能下的关键。

## 2. 代理地址的作用

`src/proxy.rs` 的完整说明写在模块注释里（`L1-L7`）：

- **它是什么**：让 `dlm` 的所有对外请求走一个 HTTP / SOCKS5 代理
- **空串 = 直连**（不是错误）；清空输入框就回到直连
- **必须写端口**：`http://host:port` 或 `socks5://host:port`。
  不猜默认端口 —— 猜错等于把流量悄悄导去别处
- **密码只留在内存**：日志与错误串里只有 `Redacted` 形态，不落盘

对你现在的"网络失败"没用——那次已经定位成 VPN 没开，不是代理配置问题。

## 3. MCP 需要更新吗 —— 需要，而且落后很多

```
已装  E:\Tool\dlm\bin\dlm-mcp.exe  →  自检输出：Download Manager MCP 桥接 0.7.2
最新  0.7.7 包里的 dlm-mcp.exe     →  自检输出：Download Manager MCP 桥接 0.7.7
```

MCP 是**独立包装**（`packaging/build-mcp-package.ps1`），不和主包一起覆盖；
它靠 `接口 api 2` 这个契约和内核通信。0.7.2 之后内核加了不少东西
（视频任务、外部下载、`/api/add` 的 `video` 字段），旧桥接不会认识它们。

**结论：装 0.7.7 的 MCP 包**（`dlm-mcp-0.7.7-win-x64.zip`）。

## 4. 每次更新设置被重置

### 设置存在哪

`%LOCALAPPDATA%\dlm\settings.json` —— 与 `queue.json` 同目录
（`src/gui/mod.rs:346` 等三处：`config.queue.parent()`）。
**所以覆盖 `E:\Tool\dlm` 安装目录不会动它**，这一点我核过：文件确实在
`C:\Users\ROG\AppData\Local\dlm\settings.json`，690 字节，改于 11/27 23:15。

### 那为什么会"重置"

`Settings::load`（`src/gui/settings.rs:172-178`）：

```rust
let Ok(raw) = std::fs::read(&path) else { return Self::default(); };
serde_json::from_slice(&raw).unwrap_or_default()
```

**任何一种解析失败，都静默返回"全默认"**，而且不记录任何日志。
接着程序在设置页保存时，就用手上的"全默认"把好文件覆盖掉 —— 用户看到的就是"设置被重置"。
字段类型一旦变（比如某个值从数字改成字符串），或文件被别的东西改坏一个字符，
就是这个结果。

结构本身是 `#[serde(default)]` 的（`L30`），**新增字段不会**触发这个问题；
触发它的是"解析不了"。

### 建议

1. 解析失败时**不要**静默吞掉：留一份 `settings.json.bak`，并在日志里写清原因
2. 只有在用户真的点"保存"时才覆盖，且覆盖前先备份
3. 加一条用例：喂一个坏 JSON，断言"返回默认值但原文件被动过"

## 5. 网页插件那三处

### ① 前面为什么有个红 ✗

记录是这么加的（`browser/extension/content.js:1487-1489`）：

```js
if (msg.mode === "queue") {
  state.finished.unshift({ name: msg.name || "下载任务", queue: msg.id });
```

**没写 `ok: true`**，而渲染按 `item.ok ? "✓" : "✕"` 画图标（`L842`）。
于是"已加入队列"这条明明成功了，却顶着个红叉。是 bug，不是设计。

### ② 「继续」为什么没意义

`canResume`（`L895-899`）：

```js
if (!item || item.ok) return false;
if (item.queue) return true;          // ← 只要有 queue id 就给「继续」
return !!item.url && (item.canceled || item.failed);
```

那个 `queue` 分支本来是为"任务被停了要续跑"准备的；"刚加入队列"也满足它，
于是给出一个点了没反应的「继续」。**应该显示「打开」**（把桌面端窗口带到前台）。

### ③ 插件能不能显示进度

能，但现在没有通道：

- 直连模式下宿主会推 `progress`（`background-0.2.19.js` 的 `op === "progress"` → `job-progress`）
- **队列模式没有**：任务进了 GUI，宿主不再知道它的进度

两条可行的路：

- **A（推荐）** 插件直接问 GUI 的 HTTP 口（`/api/tasks` 一类只读接口），
  用整体进度条渲染；不用改宿主协议
- **B** GUI 把进度推给宿主 → 宿主转给扩展；改动面大

### 仍缺的两条（都已定好做法，只差实现）

**② 插件显示队列进度**
`GET /api/tasks` 已经存在（`src/gui/http.rs:71`）。做法二选一：
- A（推荐）宿主新增 `task-progress` op：拿 endpoint 的 port+token 去 GET `/api/tasks`，
  回一份精简进度；SW 用 `req` id 把回执路由给发起请求的 tab；内容脚本每 2 秒轮询一次，
  只在面板打开时轮询。
- B 内容脚本直接戳 `127.0.0.1:<port>`：要 GUI 那边加 CORS 头，并且 token 要能传给页面
  脚本（现在只走 Native Messaging）——不推荐。

**③ 把 yt-dlp 进度写回队列**
现在只剩"日志里有进度、列表里没有"。做法：`dlm.exe --video` 收一个
`--queue-progress <文件>`，每 2 秒原子写 `{total_len, delivered}`；
GUI 的 runner 在 tick 里读它并更新 store（与断点文件同一套节流思路）。
这样列表才有大小与百分比，详情面板的曲线也才有数据。
