## 这一轮要解决什么

一句话：**让「从浏览器点到下载」这条链路完整、可靠、看得见。**

拆成三件事：

1. 浏览器下载必须落进桌面端队列 —— 现在带 Cookie 的下载**整条链路对桌面端不可见**
2. 队列不可达时不许静默降级 —— 现在会安静地起一个独立进程，用户以为没生效
3. 队列里的任务要能看见分段覆盖 —— 数据早就在断点文件里，只是被丢掉了

---

## 根因（已实测，不是推断）

### A. 同步 bug

**复现方式**：起一个空队列的 GUI，按原生消息协议（4 字节小端长度 + JSON）给
`dlm-native-host.exe` 发两次 `download`，中间用 `GET /api/tasks` 查队列。

| 输入 | 宿主返回 | 桌面端队列 |
|---|---|---|
| 不带 cookie | `mode: queue` | 出现 `a.bin` ✓ |
| 带 cookie（`sid=abc123`） | `mode: direct` | 仍是 `['a.bin']`，**b.bin 不在** ✗ |

**链条**（每一环都有代码位置）：

1. `browser/extension/background-0.2.16.js:221` 的 `submitPage` **每次都带 cookie**：
   `cookieHeader(url)` 把该 URL 下所有 cookie 拼成串，没有则空串。
   真实站点的会话 cookie 基本非空 ⇒ 绝大多数下载都命中下一条。
2. `src/host.rs:388` 的分流规则：`if cookie.is_none() && !hls { try_queue(...) }`
   —— **有 cookie 或 HLS ⇒ 直接跳过队列**。
3. 直连 = `src/host.rs:466` 起一个独立的 `dlm.exe --url … --out-dir …`，
   **不带 `--queue`**。这个进程下完就退出，`dlm-gui` 从头到尾不知道它存在。
4. 只有「无 cookie + 非 HLS + 队列可达」才会 POST `src/host.rs:712` 的 `/api/add`。

**更深一层（这才是真正的缺口）**：`src/queue.rs:38` 的 `Task` **没有 cookie 字段**，
`src/gui/http.rs:349` 的 `AddFields` 也不收 cookie。
带 Cookie 的下载在**架构上**就进不了队列。

这个取舍写得很明白，在 `src/state.rs:9`：
> 「口令不进这个文件，靠"结构里没有这个字段"保证。」

原则本身没错，但它把浏览器下载挡在了门外 —— 浏览器下载恰恰是最需要带 cookie 的那一类。

**第二条静默路径**：`src/host.rs:402` 的 `QueueOutcome::Unavailable => {}`。
GUI 没开、端点文件过期、解析失败，都不报错，直接落到直连 —— 同样不可见。
即使无 cookie，只要 GUI 没起，用户也只会看到"什么都没发生"。

### B. 分段看不到

- `src/queue.rs:474` 的 `progress()` **已经在读** `.dlm.json` 里的 `segments`，
  但它只把区间求和当 `delivered`，几何信息全丢了。
- 实时分段只存在于引擎内存：`src/engine.rs:304` 的 `RunSnapshot` 八格里没有任何几何字段；
  `src/scheduler.rs:245` 的 `snapshot_intervals()` 是现成的，却从没被接出去。
- 断点文件最多每 5 秒落一次（`src/consts.rs:14`），所以「第一档」的刷新精度就是这个数。

## 总原则

1. **一步一提交、一步一全绿**：每步跑 `gates.ps1`，数字只增不减。
2. **纯逻辑先测后画**：区间归一化、加解密、URL 判断都做成纯函数 + 用例，UI 只负责画。
3. **引擎只读不动**：调度器有 40+ 条用例守着，这一轮不许改它的行为。
4. **凭证只在内存与密文里**：绝不进 argv、绝不进 `queue.json`、绝不进日志。
5. **不碰发布链**：`latest.json` / `main` 分支等到步骤 6 单独点头。

## 步骤 1：C 止血 —— 队列不可达要说话

**现状**：`src/host.rs:402` 静默降级，用户无法区分「进了队列」和「起了个独立进程」。

**改法**：

- `QueueOutcome::Unavailable` 带上原因：端点文件不存在 / 解析失败 / 连接失败 / 非 2xx。
- `download()` 直连分支的回复里加 `reason` 字段（保留 `mode: "direct"`，不改变既有字段）。
- 扩展侧 `background-0.2.16.js` 收到 `mode: "direct"` 时，悬浮球显示
  「已交给 dlm（独立进程，不在窗口里）」—— 把"为什么桌面端看不到"直接说清楚。
- **保留直连兜底**：GUI 没开时用户仍希望下得动，只是必须显式告知。

**判据**

- 宿主用例：删掉端点文件后 `download` 的回复含 `mode:"direct"` 且 `reason` 非空。
- 宿主用例：端点文件内容被改坏（非法 JSON）也走同一条，`reason` 与"文件不存在"可区分。
- 扩展侧静态断言：`job-accepted` 带 `mode:"direct"` 时不当作"已入队"来显示。

## 步骤 2：A3 队列支持 Cookie（DPAPI 加密落盘）

### 数据流

```
扩展 --cookie--> 宿主 --{op:"download", cookie}-->
  POST /api/add {..., cookie}          （本机回环 + token，与现有控制口同一条防线）
    --> GUI 立刻 DPAPI 加密写到 <data>/secrets/<task_id>.bin，明文只活一帧
    --> runner 起 dlm.exe 时读密文、解密，走 --cookie-stdin
```

**关键点**：`--cookie-stdin` **已经支持**（`src/cli.rs:295`，且有互斥用例
`cookie_stdin_trims_and_conflicts_with_cookie`）。所以 CLI 一行都不用改。

### 改动点

1. `src/queue.rs:38` `Task` 加 `#[serde(default)] pub needs_secret: bool`
   —— **只记「有凭证」这个事实，不记内容**，与 `state.rs` 里 `needs_secret` 同一思路。
2. `src/gui/http.rs:349` `AddFields` 加 `cookie: Option<String>`；`parse_add_fields` 读它。
   `AddFields` 的 `Debug` 要像 `task.rs:24` 那样掩码，别把 cookie 打进日志。
3. 新增 `src/gui/secrets.rs`：
   - `pub fn put(data_dir: &Path, task_id: &str, cookie: &str) -> Result<()>`
   - `pub fn take(data_dir: &Path, task_id: &str) -> Option<String>`
   - `pub fn remove(data_dir: &Path, task_id: &str)`
   - 实现：`#[link(name = "crypt32")]` 的 `CryptProtectData` / `CryptUnprotectData`，
     带 `CRYPTPROTECT_UI_FORBIDDEN`（不许弹 UI 卡住后台线程）。
   - FFI 写法照 `src/gui/clipboard.rs:141` 的先例（那里已经 `#[link(name = "user32")]`，
     本项目不引 crate 处理这类系统能力）。
   - 非 Windows：`#[cfg]` 掉，返回 `Err("仅 Windows 支持")`，不留半截实现。
4. `src/gui/runner.rs:357` 附近：`needs_secret` 时 `take()` 解密 → `--cookie-stdin` →
   把 cookie 写进子进程 stdin 后立刻丢掉本地 String。
   解密失败 ⇒ 任务失败，文案「凭证已过期，请从浏览器重新发送」。
5. 任务完成 / 删除 / 终态失败：`remove()` 掉密文，不留孤儿文件。

### 为什么是 DPAPI（而不是 A1 明文 / A2 不落盘）

| 方案 | 问题 |
|---|---|
| A1 明文存 `queue.json` | cookie 就是会话凭证，明文躺在 `%LOCALAPPDATA%` 是实打实的降级 |
| A2 完全不落盘 | 重启后恢复不了，「暂停 → 关软件 → 明天继续」会**静默失效**——这恰恰是下载器最常见的用法 |
| **A3 DPAPI** | 密文只在**当前 Windows 用户**下可解，与浏览器存 cookie 同级；代价约 60 行 FFI |

### 判据

- 单测：加解密往返一致；**密文里逐字节搜不到 cookie 明文**（断言子串不存在）。
- 单测：`take()` 在密文被替换/截断时返回 `None` 而不是 panic。
- 集成：`/api/add` 带 cookie → 任务入队、`needs_secret=true`、`secrets/` 出现密文，
  且 `queue.json` 全文**没有** cookie 字样。
- 反例：删掉密文后恢复任务 → 明确失败并给可操作文案，**不许静默从头下**。
- 端到端：本地起一个「需要 Cookie 才给文件」的 HTTP 服务，真跑一次下载成功。

## 步骤 3：分段覆盖集可视化（第一档）

### 数据

- 新增 `queue::segments(out_dir, name) -> Option<(u64 /*total*/, Vec<(u64, u64)>)>`：
  把 `src/queue.rs:474` 现有的读取逻辑拆成「读」+「求和」两半，几何单独吐出来。
- `src/gui/snapshot.rs:114` 的 `TaskView` 加 `pub segments: Vec<(u64, u64)>`。

> ⚠️ **两个 `TaskView` 不是同一个东西**
> - `src/gui/snapshot.rs:114`：界面用的视图，`Serialize` only，喂 `/api/tasks` 与绘制
> - `src/state.rs:81`：磁盘格式里的任务视图（`Task` 去掉口令）
>
> 只改**前者**。改错就会出现 `.dlm.json` 里多一份 `segments`（与 `state.segments` 重复），
> 既涨体积又制造两份真相。

### 画法

- **列表行**：进度条改成「分段条」——已覆盖区间涂实、空隙留白。
  没有 `segments` 时**退回现有单色条**，不许出现一条假满的条。
- **右侧抽屉**：一块「分段」卡片，按 total 长度画出条 + 段序号 / 区间 / 大小。
- 图例一句：「每 5 秒刷新（读断点文件）」——说清精度，别让人以为是实时。

### 判据

- 纯函数：`(total, segments)` → 归一化到 `[0,1]` 的绘制矩形；含
  「极小段至少 1 设备像素」「重叠/相邻区间合并」「total 为 0 或缺失时返回空」。
- 渲染：构造 3 段的 `TaskView`，一帧能画出 3 个实心块且都不超出行宽。
- 诚实：无断点文件时显示「暂无分段信息」。

## 步骤 4：P1 浏览器下载全量接管

**现状**：只有右键 / 点击 / Alt+点击能接管。用户在浏览器里自己点「保存」的下载接不到。

`browser/extension/manifest.json` 的 permissions **已经包含 `downloads` 与 `webRequest`**，
不需要新增权限。

**改法**

- `background-0.2.16.js` 加 `chrome.downloads.onCreated` 监听；
  命中就 `chrome.downloads.cancel(id)` + 把 URL / referer / cookie 交给 dlm（走步骤 2 之后的队列路径）。
- **默认关，用户显式开启**。接管别人的下载是侵入性行为，不能默认开。
  开关放进「组件」页（那一页本来就是"四个组件"的状态面板）。
- 区分「用户主动另存为」与「站点 JS 自动触发」：后者默认不接管。
  `DownloadItem` 本身没有这个标记，用 `webRequest` 记下发起者（initiator）来判断。
- `chrome.downloads.cancel` 失败（例如下载已开始）要放行，并明确告知"这次没接住"。

**判据**

- 扩展静态用例：新权限读取、开关默认值、initiator 判断的纯函数。
- 真机：打开开关后点一个链接保存 → 出现在 dlm 队列（带截图）。
- 反例：开关关闭时点保存 → 浏览器原生下载照旧，不被打断。

## 本轮不做（明确边界，别自己开工）

| 项 | 为什么不做 |
|---|---|
| **分段实时档**（IDM 那种每连接一条） | 要动 `RunSnapshot` + 改进度行协议，属独立一轮；先看第一档够不够用 |
| P2 多源 / 镜像加速 | 收益大但要重做 fetch 层，与 A3 无冲突，排下一轮 |
| P3 分块校验（Metalink 式） | 同上，依赖 P2 的分块模型 |
| P4 视频嗅探 | `webRequest` 权限已有，但属独立功能 |
| P5 队列优先级 / 并发分组 | 属调度策略，需要先设计 |
| P6 HLS 直播 / DASH | HLS 点播已实现（顺序拼接 + 合并）；直播是另一个工程 |
| P7 BT / 磁力 | **建议明确不做**：另一套协议栈 + 法律风险 |
| P8 远程控制 | 本地 HTTP 控制口已有，加鉴权即可，但属独立功能 |
| `--cookie` 走命令行参数 | **永不**：进程列表对所有本机用户可见，凭证会泄漏到 `tasklist` 里 |

## 风险与应对

| 风险 | 应对 |
|---|---|
| DPAPI FFI 写错导致崩溃 | `unsafe` 块收窄；失败一律返回 `Err` 不外抛；单测覆盖往返 + 密文损坏两条 |
| cookie 泄漏进日志 | 逐点检查日志写入；加一条用例：抓 runner 的 stderr，断言不含 cookie 明文 |
| `chrome.downloads.cancel` 打断用户正常下载 | 默认关；只接管显式开启的；拿不到 URL 时放行；失败明确告知 |
| 分段条在超长文件上抖动 | 归一化到设备像素整数边界；极小段给 1px 最小宽并合并相邻 |
| **两个 `TaskView` 混淆** | 计划已点名；改 `gui/snapshot.rs` 后 `cargo doc` 确认 `state.rs` 的没被波及 |
| cookie 入队后任务被复制到别的机器就失效 | 密文是 DPAPI、绑当前用户；跨机恢复必然失败，文案要说清"请重新发送"而不是"文件损坏" |

## 验收标准（全做完时逐条对照）

1. 浏览器右键下载（带 cookie）→ 出现在桌面端队列，可暂停 / 继续
2. 浏览器自身「另存为」（开关打开）→ 同上
3. 桌面端没开 → 扩展明确告知「已交给独立进程」，不静默
4. 队列里的任务 → 列表行与抽屉都能看到分段覆盖
5. `queue.json` 与所有日志里搜不到任何 cookie 明文
6. 门禁全绿（fmt / lib / bins / integration / clippy / extension / ext-guard / ps-enc）
7. 每步都有证据截图或实测数字进 `docs/evidence/`
