## D. 决策记录：**不复用 IDM 的驱动**（2026-11-13，用户提出后否决）

用户曾提议"直接复用 IDM 的 `idmwfp64.sys` 改一改"。结论：**三重不可行**，写入档案免得以后重提。

1. **签名墙**：该驱动是微软 WHQL 签名（`CN=Microsoft Windows Hardware Compatibility Publisher`），签的是那份二进制的哈希。改一个字节 → 签名失效 → DSE/HVCI 拒绝加载；自签内核驱动只能靠关驱动签名强制/关 Secure Boot，杀软会直接拦。
2. **接口墙**：驱动不独立工作，靠私有 IOCTL 与 `IDMNetMon64.dll`/`IDMan.exe` 通信，`1001` 端口协议是数字 opcode 数组且无文档。"复用"实际等于逆向整条私有链路再重写。
3. **版权墙**：Tonec 商业软件，无源码；改造再分发违反许可，公开仓库会直接吃 DMCA。

**替代路线**（若将来真需要系统级可见性）：WinDivert（LGPLv3、官方签名分发）> ETW 观察（只能看不能接管）> 自研驱动（需 EV+attestation，商业才划算）。当前选择仍为**扩展层接管**。

## E. downloads 接管的前置依赖（本次侦察发现）

现有 native 消息协议**没有"任务已建立"的同步回执**：`port.postMessage(task)` 之后只有 `progress`/`done` 事件，`submitPage()` 的返回值只代表"交给宿主了"，不代表 `queue.add` 成功。

因此接管必须补一个协议消息：`op:"add"` 带 `request_id` → 宿主在 `queue.add` 返回后回 `{op:"accepted", request_id, ok, job}`。**先收到 `accepted: ok` 再 `chrome.downloads.cancel()`**；超时（2s）则不动浏览器下载，只记一条日志。

v1 参数：默认**关**；白名单扩展名（zip/7z/rar/iso/exe/msi/mp4/mkv/flac…）；复用 A3 站点黑名单；仅当 `bytesReceived === 0` 时取消；每站点可单独关闭。

### C1 的三条路线（需用户选一条）

1. **只增强嗅探（推荐先做）**：接住页面**已经暴露**的直链 / HLS / DASH manifest，不破解签名、不解密、不碰 DRM。工程可控，风险最低。
2. **接可选外部引擎**（如 yt-dlp）：dlm 只负责"识别页面 → 调外部程序 → 接回进度"。下载能力由用户自己安装的工具提供，dlm 不打包、不内置规避逻辑；需要单独评估许可与分发方式。
3. **自研站点解析**：要做签名算法逆向、播放器 JS 跟进、限流对抗。**维护成本极高**（平台改版即失效），且公开仓库的合规风险最大。

### B 节第 3 条的准确说法（修正）

- **裸 WebSocket 固定端口**：IDM 扩展连 `ws://127.0.0.1:1001` 无鉴权，本机任何进程都能冒充扩展或冒充下载器。dlm 用 native messaging（由浏览器校验扩展身份）+ 带 token 的 HTTP，这是**明确保留**的设计。
- **proxy / management**：让扩展能改系统代理、能启停其他扩展 —— 权限面过大，**不做**。
- **cookies**：dlm 扩展**已经在用**（用于带登录态的下载与嗅探），不是"不做"项；边界是只把 Cookie 交给本机宿主、不上传。
