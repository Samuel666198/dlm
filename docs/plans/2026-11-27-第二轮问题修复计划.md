## 1. 下载时弹出黑色终端窗口

**用户原话**：「有时下载会出现终端弹窗 如图1」

**根因（已实测，不是推断）**

- `dlm.exe` 是**控制台子系统**（PE subsystem = 3），`dlm-gui.exe` 是 **GUI 子系统**（= 2）
- `src/gui/runner.rs:638` 起子进程时**没有** `creation_flags(CREATE_NO_WINDOW)`
- GUI 子系统进程起控制台子进程而不加这个标志 ⇒ Windows 分配一个新控制台 ⇒ 黑窗口

对比：`host.rs:535`（原生宿主起 dlm.exe）、`gui/mod.rs:857`（起 updater）、
`mcp_install.rs:237` **都加了**，只有 GUI 的 runner 漏了。

**实测证据**：让 GUI 起一个任务，然后查 `dlm.exe` 的子进程 —— 有 `conhost.exe`：

```
dlm.exe pid=30612   child: conhost.exe pid=32940   ← 说明分配了控制台
```

加了 `CREATE_NO_WINDOW` 之后不会有这个子进程。

**为什么用户说"有时"**：短任务窗口一闪而过；长任务（比如他那个 10.9 GiB 的模型文件）
窗口一直挂着。不是偶发，是每次都有。

**改法**：`runner.rs` 的 `Command::new(&config.dlm_exe)` 加

```rust
#[cfg(windows)]
{
    use std::os::windows::process::CommandExt;
    const CREATE_NO_WINDOW: u32 = 0x0800_0000;
    command.creation_flags(CREATE_NO_WINDOW);
}
```

顺带**把这三处常量收拢到一处**（现在 `host.rs` / `mod.rs` / `mcp_install.rs` 各写了一份），
避免下次又漏。建议新增 `src/gui/proc.rs` 或放到 `consts.rs` 里一个 `no_window(&mut Command)`。

**判据**：起一个任务后，`dlm.exe` **没有** `conhost.exe` 子进程；
且任务仍能正常下载（不能因为加了标志而让子进程读不到 stdin / 写不了日志）。

## 2. 桌面端没开时，插件直接下载会怎样

**用户原话**：「如果桌面程序没有打开 网页插件直接下载会有什么问题吗 这个有没有检查过」

**查清了，结论：能下，但会和桌面端变成两套账。**

链路：

1. 扩展投递给原生宿主（`com.dlm.host`，注册表指向 `E:\Tool\dlm\bin\dlm-native-host.exe`）
2. 宿主发现队列不可达（`%LOCALAPPDATA%\dlm\gui\endpoint.json` 不在或被清）
3. 按设计**降级直连**：起一个自己的 `dlm.exe`
4. 落点取宿主配置；本机 `%LOCALAPPDATA%\dlm\native-host\config.json` **不存在**
   ⇒ 走默认：`dlm.exe` 与宿主同目录、**落点 `%USERPROFILE%\Downloads`**、日志到宿主的 log 目录

### 用户的关键提问：CLI 跑了，桌面端为什么没记录？

> 用户原话：「不是有 cli 吗 然后插件请求的不相当于是通过 cli 的吗 按理来说桌面端是会有记录的吧」

**答案：CLI 是"干活的手"，不是"记账的账本"。**

- `dlm.exe` 是**无状态的单文件下载器**：给它 `--url --out-dir`，它下完就退出；
  它唯一的"状态"是目标文件旁边的 `<目标>.dlm.json` 断点文件（成功收尾时默认删掉）。
- 桌面端的"记录"是 `%LOCALAPPDATA%\dlm\queue.json`，而 **`QueueStore` 只被 `dlm-gui` 使用**
  （`src/bin/dlm-gui.rs:22`、`src/gui/mod.rs:327`），CLI 里根本没有写队列的代码。
- 所以"CLI 跑过一次"≠"桌面端有记录"。**只有 GUI 自己派发的任务才进队列。**

两条路的区别：

| | 谁 spawn 的 dlm.exe | 谁写 queue.json | 桌面端看得到吗 |
|---|---|---|---|
| GUI 在跑 | **GUI**（读完 `/api/add` 建好任务后） | GUI | 看得到 |
| GUI 没跑 | **原生宿主**（进程内直接起） | 没人写 | 看不到 |

**顺带查清一个设计缺口**：代码里其实**有**一个"只入队不下"的标志位
（`consts::FLAG_ADD_ONLY`，命令行 `/a` 与 `--no-start` 都能解析），但
`engine.rs:592` 的文档明写：

> ⚠ 本函数不看 `FLAG_ADD_ONLY`……**全树生产代码里那个位没有任何读取点**，
> 它必须由调用方在进入 `run` 之前短路。

也就是说：**"让 CLI 把任务登记进队列"这个能力只存在于 spec 和参数解析里，从来没实现过。**
这是历史欠账，不是这一轮引入的。

### 落点其实是一致的（修正我上一版的说法）

GUI 默认落点 `%USERPROFILE%\Downloads`（`dlm-gui.rs:95`），宿主默认也是同一个目录
（`host.rs:92`）。本机 `settings.json` 里 `out_dir` 是**空字符串**（等于用默认），
所以**现在两条路的文件落在同一个目录** —— 差别只在"有没有那条任务记录"。

> 一旦有人在设置里改了「保存目录」，两条路就会真的分叉。这一点上一版计划写成
> "两个目录"，不准确。

### 决定（用户 2026-11-27）：浏览器下载必须落在 GUI 里；GUI 没开就**先自动打开它**

> 用户原话：「建议下载需要打开 gui，没有打开先自动打开」

比"拒绝"好：既不丢下载，也不再有两套账。

#### 可行性：已确认，而且很干净

两边**默认路径本来就是同一套**，所以拉起 GUI 之后不需要传任何参数：

| 项 | `dlm-gui.exe` 默认（`dlm-gui.rs:93-106`） | 原生宿主读的（`host.rs:84`） |
|---|---|---|
| 队列 | `%LOCALAPPDATA%\dlm\queue.json` | —— |
| 端点文件 | `%LOCALAPPDATA%\dlm\gui\endpoint.json` | **同一个文件** |
| 端口 | `0`（自动挑空位） | 从端点文件读 |
| 令牌 | `None`（随机生成） | 从端点文件读 |
| 落点 | `%USERPROFILE%\Downloads` | 同（宿主默认） |

`dlm-gui.exe` 是 **GUI 子系统**，直接拉起**不会闪控制台**；
它也已经有**单实例复用**（第二个实例打印 URL 后退出），所以并发拉起是安全的。

#### 实现草图（改 `host.rs`）

`download()` 的分流从"队列不可达 ⇒ 直连"改成：

```
1. try_queue()                         → 通了就进队列（现状）
2. 不通（Unavailable）⇒ ensure_gui()：
   a. 记下旧 endpoint.json 的 pid（没有就算了）
   b. 起 dlm-gui.exe（不带参数；DETACHED，不等待）
   c. 轮询 endpoint.json 直到 pid 变了 且 GET /api/tasks 能通（上限约 8 秒）
3. 起来了 ⇒ 重新 try_queue()           → 进队列
4. 还是不通 ⇒ 才降级直连，并在回复里带
   reason = "queue-unavailable" + detail，扩展照常显示「已交给独立进程」
   （**保留兜底**：不能因为 GUI 起不来就把用户的下载丢了）
```

要点：

- **只在队列不可达时才拉起**，GUI 已经开着时不重复起（单实例也会挡一层）
- `dlm-gui.exe` 的路径：`config.dlm_exe` 的同级同名替换（`dlm.exe` → `dlm-gui.exe`），
  找不到就跳过拉起、直接走兜底
- 拉起后**必须等到端点文件里的 pid 变化**，不能只等文件存在 ——
  旧文件可能还躺在那儿（上次崩溃留下的），会读到死端口
- 8 秒上限要给得出理由：GUI 冷启动要加载字体、初始化 egui，实测通常是 1–2 秒

#### 三个需要拍板的子问题

1. **拉不起来时怎么办**：我建议**保留直连兜底**（下载优先），扩展照旧显示
   「桌面端没起来，已交给独立进程」。要不要改成彻底拒绝？
2. **HLS 仍然进不了队列**：队列任务模型没有 `--hls`，所以浏览器下的 m3u8
   **即使 GUI 开着也还是直连**，仍然不在列表里。两个选择：
   - 给队列加 `hls` 字段 + runner 传 `--hls`（中等改动，能让 HLS 也进列表）
   - 或者对 HLS 保留直连，并让 GUI **被动发现**它（下面那条 B 的残留价值）
3. **抑制重复拉起（用户已决定：要，且默认开启、可在设置里改）**

   > 用户原话：「3 抑制吧 可以在设置中设置 默认抑制」

   **语义**（写清楚，避免"抑制"被理解成"不拉起"）：

   | 情形 | 行为 |
   |---|---|
   | GUI 没开，**冷却窗口外**（默认 5 分钟内没自动拉过） | **拉起** GUI，把任务送进队列 |
   | GUI 没开，**冷却窗口内**（刚拉过又没了） | **不拉**，走兜底直连，扩展显示「已交给独立进程」 |
   | GUI 已经开着 | 不拉（本来也不需要），任务直接进队列 |

   也就是说：抑制的是**反复拉起**，不是"从不拉起"。第一次仍然会打开 —— 这正是上一条要求。

   **设置项**（放在设置页「集成」或「浏览器」那一组，与已有的连接数/规则同处）：

   - 名称：`抑制重复自动拉起`
   - 默认：**开**
   - 说明文案：`5 分钟内只自动打开一次；关掉则每次下载都会尝试打开`
   - 关掉它 ⇒ 每次都拉（适合"我就是希望它一直弹出来"的用户）

   **实现**：冷却状态不能放在宿主进程内存里 —— 原生消息宿主是**每次消息一条短命进程**，
   进程内标志等于没有。所以要落一个小文件：

   - `%LOCALAPPDATA%\dlm\gui\autolaunch.stamp`，内容只有 `{"last":"<unix 秒>"}`
   - 拉起前读它：`now - last < 300` 就跳过
   - 拉起后写 `now`（**先写再拉**更好：拉失败也算"刚试过"，避免失败时被反复重试打爆）
   - 并发：两个浏览器下载同时到 → 两个宿主同时读到旧时间戳 → 可能都拉一次。
     这没关系：GUI 是单实例的，第二个会自己退出。**不要为此加锁**，
     代价（可能的重复进程创建）远小于收益（无死锁风险）

   **为什么不放在 `settings.json` 里当"上次拉起时间"**：`settings.json` 是用户配置，
   被 UI 读写、可能被用户手改/备份还原。运行时的冷却戳混进去会让那份文件变得不可预期。
   配置（抑制开关）进 `settings.json`，运行时状态进 `autolaunch.stamp`，两件事分开。

#### 顺手保留的低成本增强（可延后）

GUI 扫 `out_dir` 里的 `*.dlm.json`，把**外部进程正在下的任务**显示为「外来任务」。
它只对 HLS 之类的直连残留有用（成功收尾会删断点文件，所以只能看到进行中/失败的）。
如果上面第 2 个子问题选了"HLS 也进队列"，这条就可以完全不做了。

**判据**

- 关掉 GUI ⇒ 从浏览器下载一条 ⇒ **GUI 被自动拉起**，任务出现在列表里并可暂停/续传
- GUI 已开着 ⇒ 下载一条 ⇒ **不会**出现第二个 GUI 实例
- 端点文件是**上次崩溃留下的旧文件** ⇒ 仍能正确识别为"没起来"并重启 GUI
  （用例：写一个 pid 不存在、端口没人监听的 endpoint.json）
- 拉起超时 ⇒ 仍能下载成功（走兜底），且扩展显示「已交给独立进程」
- **抑制生效**：连点两条下载（GUI 已被关掉）⇒ 第一条拉起 GUI，第二条**不再拉起**
  （冷却窗口内）；把 `autolaunch.stamp` 的时间改到 10 分钟前 ⇒ 又会被拉起
- **关掉抑制**（设置项）⇒ 冷却窗口内也会拉起

## 3. 分段区间太多（111 / 353 个）

**用户原话**：「如图，区间是不是分太多了」

**已查清的部分**

- 这两个数字来自断点文件的 `segments` 数组原始长度（抽屉里写的是「断点里 353 个区间」）
- **画的时候是合并过的**：`segment_bar::spans()` 会把相邻/重叠区间并起来再画
  ⇒ 于是出现"文字说 353 段、图上看着像一整条"的不一致
- 为什么碎这么多：8 条连接并行推进 + 中途重分片，覆盖集本来就是碎片的；
  每个 64 KiB 窗口完成就记一段，10.9 GiB 的文件碎成几百段不奇怪

**要做的两件事**

1. **文案改成"合并后"的数量**（或两个数都给：「覆盖集 353 段，合并后 12 段」），
   别让文字和图形说两件事
2. 顺带评估：落盘时要不要**压缩覆盖集**（相邻区间合并后再存），
   能显著减小 `queue.json`/断点文件体积；但要注意这会改动 `state.rs` 的落盘格式，
   属独立改动，**本轮不做，只记录**

**判据**：抽屉里显示的数量与图上色块数一致；有一条用例断言"353 段输入画出 N 块、文字也是 N"。

## 4. 暂停后继续，一直卡在「排队中」（**最高优先级**）

**用户原话**：「暂停之后继续就会一直显示在排队」

**已实测复现**：`/api/pause` → `/api/resume` 之后 12–20 秒内 `status` 一直是 `queued`，
`tasklist` 里**没有任何 `dlm.exe`**，不是"在下但没刷新"。

**根因（已确认）**

暂停时**没有归还 host 连接预算**：

- `runner.rs:198` 的 `Ticket::Pause`：把子进程从 `children` 里 `remove` + `kill`，
  清 `reserved` / `last_delivered`，**但没有 `state.gate.give_back(&id)`**
- `apply()` 拿不到 `state.gate`（注释写着"要动 tuning 与 gate 的两者都不在这条路的参数里"），
  真正的 `give_back` 只在**子进程退出**那条路里做（`runner.rs:491`）
- 而暂停已经把子进程从 `children` 移除 ⇒ 退出那条路**永远看不到它** ⇒ 用量永久挂在账上

于是恢复时派发判据 `runner.rs:623`：

```rust
state.gate.allows(&t.url, plan_for_task(t, tuning).1)
// = can_start(used, want, per_host) = used + want <= per_host
```

默认 `connections = 8`、`per_host_connections = 8`
⇒ `8 + 8 <= 8` 为**假** ⇒ 这个任务被 `find` 跳过 ⇒ 没有别的任务 ⇒ `break`
⇒ **永远不派发**，直到重启程序（重启后 usage 表是空的）。

**更广的影响**：同一 host 上只要有任务被暂停过，之后**同 host 的新任务也起不来**。

**改法**

1. `Ticket::Pause` / `Ticket::Remove` 里补 `gate.give_back(&id)`。
   因为 `apply()` 碰不到 gate，两种做法：
   - 把 `Pause` / `Remove` 挪到主循环里就地处理（像 `ApplyRuntime` 那样），或
   - 给 `apply()` 多传一个 `&mut HostGate`
   我倾向**前者**：与既有 `ApplyRuntime` 的处理方式一致，不用给 `apply` 加参数
   （它已经有 7 个参数，clippy 那个上限已经在边上了）
2. 顺带查一遍**还有哪些路会丢 `give_back`**：`Remove`、删除任务、程序退出时 `drain` 掉
   `children`（`runner.rs:88`，那条路会 `kill` 但不 `give_back`，反正要退了，可不管）。

**判据（必须有回归用例）**

- 单测：`pause` 之后 `gate.usage[host]` 回到 0
- 集成：`/api/add` → 等 running → `/api/pause` → `/api/resume` →
  **N 秒内 status 变回 running 且 `tasklist` 里有 dlm.exe**
  （当前行为会红，这条用例就是护栏）
- 变异验证：把 `give_back` 注回去删掉，用例必须变红

**这是本轮唯一"功能不可用"级别的缺陷**，建议第一个修。

## 5. 右键指向可下载按钮时，只剩「下载本页所有链接」

**用户原话**：「右键下载是下载本页所有链接，就算在一个可下载的按钮上右键也不会变」

**根因（已确认）**

`background-0.2.16.js:257` 建了两个菜单项：

| id | 标题 | contexts |
|---|---|---|
| `dlm-download` | Download with dlm | `link, image, video, audio` |
| `dlm-page-links` | 下载本页所有链接 (dlm) | `page` |

点击处理（`:383`）：

```js
const url = info.linkUrl || info.srcUrl;
if (!url) return;              // ← 按钮上没有这两个值时，这个菜单项直接哑掉
```

一个用 JS 触发下载的**按钮**（`<button>` / `<div>` / 带 `download` 的 `<a>` 但 href 为空）
既不是 link 也不是 image/video/audio ⇒ `dlm-download` **没有可用的 URL**（显示了也立刻 `return`）。

> **待真机确认的一点**：`page` 上下文的菜单项在右键点击页面内元素时是否一定出现。
> 按 Chrome 文档「page = 右键点在页面上」，实际表现通常是会出现的 —— 但这一条我**没有实测**，
> 动手前先手动右键一个按钮确认菜单里有几项。用户看到的现象（只剩"下载本页所有链接"）
> 与此一致，但现象不等于机制。

**改法**

1. `content.js` 加一个 `contextmenu` 监听，把**被右键的那个元素**记下来：
   往上找最近的 `<a href>` / `[data-url]` / `[data-href]` / `<video src>` / `<source src>`，
   都找不到就记 `null`（并记下 `location.href` 兜底）。
2. `background` 在 `contextMenus.onClicked` 里，若是 `dlm-download` 且 `info.linkUrl/srcUrl` 都空，
   就 `chrome.tabs.sendMessage(tab.id, {op:"what-was-right-clicked"})` 问 content，
   拿到 URL 后再投递。
3. 菜单**文案要跟着变**：右键在链接上 → 「下载这个链接」；右键在空白处 →
   「下载本页所有链接（需确认）」。Chrome 的 contextMenus 不能逐次改文案（`update` 可以，
   但要在 `contextmenu` 时改，成本高），所以**先用固定文案 + 行为正确**，
   文案区分作为可选优化。

**判据**：在一个 `<button>` 上右键（页面里有个 JS 触发下载的按钮），
点「Download with dlm」能下到那个文件；内容脚本侧用例覆盖"从被点的元素往上找 URL"。

## 6. 「下载本页所有链接」必须有二次确认

**用户原话**：「若实在要下载所有链接需要二次确认」

**现状（已确认，而且要特别指出）**

`background-0.2.16.js:354` 的 `downloadPageLinks`：

```js
func: () => Array.from(document.links, (a) => a.href)
...
if (!/^https?:\/\//i.test(href)) continue;
if (host !== pageHost) continue;      // 只留同站
picked.push(href);
if (picked.length >= 50) break;       // 最多 50 条
```

**完全没有扩展名过滤** —— 同站的所有 http 链接（包括导航页、文章页、分类页）都会被入队。
这比"检测能力退化"更值得先修：一次误点就是 50 条垃圾任务。

**改法**

1. 入队前**先在页面里弹出确认层**（content.js 已有 `state.confirm` 机制，可复用），
   列出将要下载的条目（前 10 条 + "共 N 条"），用户点「确认」才提交
2. 确认层里**默认勾选按扩展名过滤后的子集**，并提供「全部」开关
3. 后台这条路径也应该带扩展名过滤（与 `collectFileLinks` 用同一份 `FILE_LINK_RE`），
   别再抓 `document.links` 全量

**判据**：点菜单后**不立即入队**；页面出现确认层；取消则队列不变；
确认后队列数量与确认层显示的数量一致。

## 7. 页面链接检测"似乎退化"

**用户原话**：「现在检测页面下载链接能力似乎有退化」

**先说查到的事实**

- 正则**没有被裁剪**：`content.js` 的 `FILE_LINK_RE` 与 `page-hook.js` 的 `FILE_RE`
  都是 **50 个扩展名**、两份逐字一致（`check-extension-static.mjs` 会卡这条）
- git 历史里这两条正则只被改过 3 次，都是**新增**（`5e26c173` 建、`ad22ee62` 补游离锚点、
  `66c21c36` 加 file 判定），没有删减

**所以"退化"更可能来自这两处（按可能性排序）**

1. **只测 `url.pathname`**（`content.js:992`）：
   `/download?id=123&name=x.zip` 这种把文件名放在查询串里的链接**永远识别不到**。
   这不算"退化"，但会让人觉得"以前能抓到现在抓不到"。
2. **扩展重载后，已打开的标签页里 content script 已退役**：
   今天为了让用户拿到新代码，反复让他「重新加载」扩展 —— 而 Chrome 只在**页面导航**时
   才注入新的 content script。已打开的页面里那份旧脚本在上下文失效后被 `die()` 退役
   （这是 2026-11-18 修的刷屏问题），于是**这个页面从此什么都不检测**，直到刷新。
   `die()` 会在悬浮球里留一句「扩展已更新，刷新页面生效」，但很容易被忽略。

**改法**

1. `collectFileLinks` 的判据从 `url.pathname` 放宽到 `url.pathname + url.search`
   （仍不匹配 hash，避免误抓锚点）
2. 退役提示加强：`die()` 不只在球里写一句，还要把角标设成醒目的状态，
   并且**顺手提示"刷新页面"**（可选：提供一键 `location.reload()`，但要用户点）
3. 检测能力加一条可验证的基线：把"一个含 8 种链接形态的静态页面"做成回归用例
   （`verify-media-sniff.mjs` 已有类似的），以后谁改动正则/扫描逻辑都能立刻看到少抓了哪种

**判据**：查询串带文件名的链接能被抓到；扩展重载后老页面明确提示需要刷新。

## 8. 顺带并入的两条旧待办

### 8.1 命令面板搜索结果过长冲出屏幕
根因与建议见上一份计划「后续待办 1」。要点：`palette.rs:150` 的 `egui::Window`

### 8.2 扩展版本号未随代码升级，组件页会假绿
0.7.4 的扩展代码改过但 `manifest.version` 仍是 `0.2.16`，

被判成「与磁盘一致」。**这次发版必须升到 0.2.17**，
并考虑把对账改成比内容（sha256 或构建标识）。

## 风险与注意

- **#4 的修法会动 `apply()` 的参数或把 Pause/Remove 挪位置** —— 这是本轮唯一碰
  "调度主干"的改动，必须配一条端到端回归用例，并做变异验证。
- **#1 加 `CREATE_NO_WINDOW` 后要确认子进程仍能读 stdin**（`--cookie-stdin` 那条路）。
  控制台标志与管道无关，但要在实测里确认，不能"应该没事"。

  所以发布说明里要把"刷新页面"写清楚。
