# 组件页 + 设置窗收敛 · 实施计划

> 2026-11-16。承接 [`2026-11-15-0.7.0-完成后交接.md`](2026-11-15-0.7.0-完成后交接.md) 末尾的欠账表，
> 以及 2026-11-15 现场走查的三条结论（设置窗溢出、「获取 dlm-mcp」只是开网页、版本信息四套口径）。

## 这一轮要解决什么

用户原话：**「专门加一个管理内核 / mcp / 网页插件的页面，把高级里的版本也整合进去」**，
外加截图指出的设置窗右侧溢出。

根因是同一个：程序有四个组件（桌面端+内核、MCP 桥接、浏览器扩展、更新通道），
但每个组件的信息散在四处、各有各的说法：

| 位置 | 现在显示什么 | 问题 |
|---|---|---|
| 高级页 `version_block`（`settings_ui.rs:717`） | 桌面端 / 内核 / 扩展 / MCP 四行 | 混在"设置项"里，且内核版本取清单值而非 `dlm.exe --version` |
| 浏览器扩展页（`:630`） | 运行中 / 磁盘上 / 内置 三个扩展版本 | 第二套扩展口径，与上一行不同源 |
| Agent 接入页（`:788`） | 只判断 `dlm-mcp.exe` 在不在 | 没有版本号 |
| 状态栏（`status.rs:72`） | `v0.7.0` 纯文本 | 无悬停摘要，也点不到组件页 |

## 总原则

1. **一步一提交、一步一全绿**：每步跑 `gates.ps1`，数字只增不减。
2. **纯逻辑先测**：状态判定、尺寸计算、URL 拼接都做成纯函数 + 用例，UI 只负责画。
3. **不碰发布链**：`latest.json` / `main` 分支 / `README.md` 一律不动（对外动作需单独授权）。
4. **诚实分支**：探测不到写「未知」，不写「未安装」；装不进去就说装不进去。

## 步骤 1：设置窗尺寸随主窗收敛（修溢出）

**现象**：`theme.rs:48` `WINDOW_MIN = [760, 480]`，`settings_ui.rs:47` `fixed_size(760, 520)`
—— 设置窗与主窗最小宽度**同宽**、比最小高度**还高 40pt**。主窗缩到接近下限时，
设置窗顶满客户区（左右各剩约 7pt，圆角与投影被切），竖向直接被裁。

**改法**：
- 新增纯函数 `settings_window_size(viewport: Vec2) -> Vec2`：取 `desired(760×520)` 与
  `viewport - 32` 的较小者，且不低于 `560×360`（viewport 更小时按 viewport 截断，不许反向溢出）。
- `max_height(420.0)` 换成 `(size.y - 100.0).max(120.0)`：窗大时仍是 420（保住现有观感），窗小时跟着收。

**判据**：纯函数用例——`(1120,700) → (760,520)`；`(760,480) → (728,448)`；极小视口不得大于视口；
渲染用例——最小主窗尺寸下仍能画出「保存 / 取消」。

## 步骤 2：组件状态模型（纯逻辑，先测后画）

新增 `src/gui/app/components.rs`：

```rust
pub enum ComponentId { Desktop, Mcp, Extension, Channel }
pub enum ComponentState { Ok, NeedsAction(String), Missing, Unknown(String) }
pub struct ComponentRow { id, title, version, state, hint }
pub fn build_rows(input: &ComponentInput) -> [ComponentRow; 4]
```

四态语义（**不能混**）：

| 态 | 含义 | 例 |
|---|---|---|
| `Ok` | 一切正常 | 扩展运行版本 == 磁盘版本 |
| `NeedsAction` | 装了但用户要做一件事 | 扩展磁盘 0.2.16 / 浏览器在跑 0.2.15 → 该重载 |
| `Missing` | 确实没有 | 找不到 `dlm-mcp.exe` |
| `Unknown` | 探测不到（≠ 没装） | 扩展没连上、读不到版本、还没检查过 |

**判据**：四态各一条用例；「探测不到」不得落到 `Missing`（这条单独钉死，它是措辞事故的源头）。

## 步骤 3：MCP 直链下载 + 解压 + 落盘（可测流程）

**现状**：`settings_ui.rs:849` 只 `open_external(MCP_RELEASES_URL)` 打开发布页，把四步手工活丢给用户。
**能力其实已在**：`updater.rs` 有 `download`(106) / `verify_file`(136) / `extract_zip`(162) / `install_extension`(276)。

**改法**：新增 `src/gui/app/mcp_install.rs`
- `mcp_asset_url(release) -> Option<String>`：由清单里的 `release` 拼
  `https://github.com/<owner>/<repo>/releases/download/v<release>/dlm-mcp-<release>-win-x64.zip`。
  **不改发布流程**（清单里没有 mcp 字段，也不允许现在加）。
- `install_from_zip(...) -> McpInstallOutcome`：解压到临时目录 → 找 `dlm-mcp.exe` →
  跑一次 `--version` 做功能校验 → 搬到 `current_exe()` 同目录。
- `McpInstallOutcome`：`Installed` / `NoAsset`(404) / `DownloadFailed` / `ExtractFailed` /
  `NoBinary` / `VerifyFailed` / `PermissionDenied`（装不进 `Program Files` 时的诚实出口）。

**完整性说明**：拼直链拿不到 sha256（清单没这个字段）。因此本轮的校验是**功能校验**
（`--version` 能跑且输出含 api 2 要求的版本），不是密码学校验；把「清单加 `mcp_sha256`」
记为后续项，动发布流程前先问用户。

**判据**：每个 outcome 一条用例；真 zip 往返一次（照 `updater.rs:530` 的写法）；
把「缺 binary」「权限失败」注回去确认变红。

## 步骤 4：`浏览器扩展` 页升级为「组件」页

- `settings_spec.rs`：`Category::Browser` → `Category::Component`，标题「组件」，
  位置仍在「界面」与「高级」之间（分类数不变，仍是 8）。
- `settings_ui.rs`：新 `component_panel(ui)` 画四张卡（用步骤 2 的 `build_rows`）；
  把 `browser_panel` 的三个版本数与动作并进「浏览器扩展」卡；
  `version_block` 从「高级」页移走（高级页只留「自动检查更新」开关）。
- MCP 卡：`Missing` 时给「下载并安装」（走步骤 3，后台线程 + 完成回执）；
  装完重新探测版本。

**判据**：四态各渲染一帧；`every_spec_belongs_to_one_of_the_categories` 的具名豁免跟着改名；
设置分类顺序用例更新。

## 风险与应对

| 风险 | 应对 |
|---|---|
| 分类改名（Browser→Component）会红一串用例 | 一次改到位：`Category` / `SPECS` / 豁免说明 / 顺序用例 |
| 真下载会联网，门禁必须离线 | 加 `DLM_NO_MCP_DOWNLOAD` 抑制开关，与 `DLM_NO_UPDATE_CHECK` 同源约定 |
| 装进 `Program Files` 需要管理员 | 映射成 `PermissionDenied`，界面退回「打开下载页」，不假装成功 |
| 跑 `dlm-mcp --version` 探测版本会起子进程 | 只在进组件页/安装完成后探测一次并缓存，不每帧跑 |
