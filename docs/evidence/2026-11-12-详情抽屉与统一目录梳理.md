# 任务详情抽屉 + 统一下载目录：梳理（2026-11-12，未动手）

**来源**：用户实测后提出三件事 + 一个缺失功能。
本文只做现状核对与方案梳理，**没有改任何代码**。

---

## 零、先纠正一个说法

用户说「点击任务条没出现预设效果（浮窗显示详细内容），**这个没有做**」。

准确说是：**做了半截**。

| 已有的 | 位置 |
|---|---|
| `selected: Option<String>` 状态 | `gui/app/mod.rs:52` |
| 点击行会设置 `selected` | `gui/app/list.rs:109-111` |
| 选中行会高亮（浅底 + 左侧 2.5pt 强调条） | `gui/app/list.rs:51-61` |
| 工具条的「继续/暂停/删除」按 `selected` 启停 | `gui/app/toolbar.rs:38-46, 81-86` |
| `theme::DRAWER_W = 372.0` 常量 | `gui/app/theme.rs:24` |

| 缺的 | 说明 |
|---|---|
| **抽屉本身** | `DRAWER_W` **零引用**，全仓只有定义那一行。没有 `SidePanel`/`Window` 去画它 |

所以「点不动」的观感来自：点了有高亮，但没有任何新东西出现。
`list.rs:39` 的注释写着「点击选中并展开详情」—— 注释比实现超前了。

## 一、任务详情抽屉

### 现在 `TaskView` 里有什么可显示的

`gui/snapshot.rs` 的 `TaskView`（12 个字段）：
`id` · `name` · `url` · `category` · `status` · `pid` · `exit_code` ·
`total_len` · `delivered` · `attempts` · `hold_until` · `created_at`/`updated_at`

另有派生：进度百分比、host、落点路径（`queue::target_path(out_dir, name)`）。

### 抽屉该放什么（按「用户点开想知道什么」排）

| 分组 | 内容 | 数据在不在 |
|---|---|---|
| 文件 | 文件名、完整落点路径、大小 | ✅ 有（落点要算） |
| 来源 | 完整 URL、host、Referer | ✅ 有 |
| 进度 | 百分比、已下载/总量、状态 | ✅ 有 |
| 时间 | 创建时间、更新时间、重试次数 | ✅ 有 |
| 动作 | 打开文件、打开所在文件夹、复制 URL、继续/暂停、删除 | ✅ `RevealMode::Open/Select` 已有 |
| 日志 | 最后几行 / 打开日志文件 | ⚠️ 路径有，读取没接 |

**结论：数据基本齐，主要工作量在画 UI + 接「打开位置」**，不需要动内核。

### 建议做法

- 用 `egui::Panel::right("drawer").exact_size(DRAWER_W)`，`selected.is_some()` 时才显示
  （注意：eframe 0.37 的 API 是 `egui::Panel::right(...)`，不是老的 `SidePanel`，见交接「坑」第 1 条）
- 抽屉里「打开文件」「打开所在文件夹」发 `Ticket::Reveal { id, mode: Open/Select }`
  —— **这条链路已经通了**（`/api/reveal` → `Ticket::Reveal` → `actions::reveal_plan`），
  UI 只是没接按钮
- 详情里点空白或按 Esc 取消选中

## 二、三件需求逐条核对

### 需求 1：统一存储位置

**现状：三个入口三个默认值，都不在软件旁边。**

| 入口 | 默认落点 | 代码 |
|---|---|---|
| GUI 队列 | `%USERPROFILE%\Downloads` | `bin/dlm-gui.rs:33` |
| 宿主直连（带 Cookie / HLS） | `%USERPROFILE%\Downloads` | `host.rs:73-77` |
| CLI | **当前工作目录** `.` | `cli.rs:447` |

也就是说：**网页插件下的文件和桌面端下的文件，现在都进用户的 Downloads**，
和浏览器自己下的一堆东西混在一起 —— 这正是用户说的「不统一」的观感来源。

**还有一个更关键的问题：设置里的 `out_dir` 不生效。**

```rust
// settings.rs:97
pub fn effective_out_dir(&self) -> PathBuf { ... }
```

**这个方法零调用点。** runner 一律用 `config.out_dir`（启动时从命令行或默认值定死）。
这和刚修的 E18 是同一类病：设置界面能改，实际不生效。

> ⚠ 不过设置面板里**现在根本没有「保存目录」这一项**（交接欠账里记着），
> 所以用户暂时改不到它 —— 但 `settings.json` 手改也没用。

**要做的**：

1. 定一个「软件自带的」默认目录。建议 `%LOCALAPPDATA%\dlm\downloads`
   （与 `queue.json` / `settings.json` / 日志同根，卸载脚本已声明保留该目录）。
   **不建议**放在 exe 同目录：便携包解压到只读位置（Program Files）会写不进去。
2. 三处默认值统一到这个目录。
3. `settings.out_dir` 真的接进 runner（`config.out_dir` 改成「命令行 > 设置 > 默认」）。
4. 设置面板加「保存目录」一项 + 「打开」按钮。

### 需求 2：快速访问（打开所在位置）

**现状：后端通了，UI 没入口。**

- `POST /api/reveal` 已实现，支持 `mode: "open"`（默认程序打开）与 `"select"`（资源管理器里选中）
- `Ticket::Reveal` → `actions::reveal_plan` → `explorer.exe /select,<path>` 全通
- **但原生窗口里没有任何「打开位置」按钮**（grep `reveal` 在 `gui/app/` 下零命中）

所以这条需求本质是：**在抽屉里放两个按钮**，接已有的链路。
外加一个「打开下载文件夹」的全局入口（工具条或状态栏）。

### 需求 3：任务同步（网页端任务显示在桌面端）

**现状：队列任务已经同步，直连任务没有。**

这是最容易误解的一条，必须分清：

| 网页端投递方式 | 落到哪 | 桌面端看得到吗 |
|---|---|---|
| 无 Cookie 直链 → 队列 | `dlm-gui` 队列 | ✅ **看得到**（队列本来就共享） |
| 带 Cookie / HLS → 宿主直连 | 宿主自己起的 `dlm.exe` | ❌ **看不到**（不在队列里） |

也就是说：**大部分网页下载其实已经同步了**，看不到的是带 Cookie 和 HLS 那两类。
用户截图里那条 `io.hdslb.com` 的任务在桌面端能显示，正好印证了这一点。

**要做的**：把直连任务也纳入队列视图。两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 直连任务完成后**补录**进队列（宿主调 `/api/add` 记一条 done 的，或新增 `/api/adopt`） | 中；要处理「同一个文件被记两次」 |
| B | 宿主把直连任务的状态**实时上报**给 GUI（进度、完成） | 大；要新开一条上报通道 |
| C | 带 Cookie 的也走队列（队列支持存 Cookie） | 大；B10 当初明确说「队列不存 Cookie」是安全决定 |

我倾向 **A**：直连任务量少（只有带 Cookie 和 HLS），完成后补录一条足够满足「看得到」。
B 的成本与收益不成比例（为了几条任务开一条实时通道）。

## 三、顺带发现的另外两个「界面在说谎」

梳理时又看到两处，和 E18 同类，一并记下：

### 1. 速度列恒显示 `—`

```rust
// gui/app/list.rs:355
fn speed_text(_task: &TaskView) -> String { "—".to_string() }
```

`TaskView` 没有速率字段。注释说「等步骤 3 收尾项」，一直没做。
用户在截图里看到的就是这个 `—`。

### 2. 「剩余」列基本恒显示 `—`

`eta_text` 只在 `paused` 时给「已暂停」、`hold_until` 时给「等待」，其余全是 `—`。
没有速率就没有 ETA，同根。

**要修的话**：runner 侧按 `last_delivered` 的两次采样算速率，加进 `TaskView`。
工作量中等，但这是「下载器主界面最显眼的两列」，值得做。

## 四、建议的优先级与分批

按「用户可感知 ÷ 代价」排：

| 批次 | 内容 | 理由 |
|---|---|---|
| **第一批** | 详情抽屉（含打开文件/打开位置）+ 下载目录统一 + 设置里加「保存目录」 | 三件事一次做完：抽屉本来就要显示落点，落点又依赖统一目录，天然耦合 |
| **第二批** | 速度 / 剩余两列真的算出数字 | 主界面最显眼，但要在 runner 加采样 |
| **第三批** | 直连任务补录进队列（需求 3 的剩余部分） | 只影响带 Cookie / HLS，量小 |

**第一批的依赖关系值得说明**：抽屉里要显示「文件保存到哪」，
而这个答案现在是三个不同的值 —— 所以「统一目录」必须和抽屉一起做，
否则抽屉里显示出来的路径会让用户更困惑。

---

## 五、需要用户先定的两件事

1. **默认下载目录放哪？** 我建议 `%LOCALAPPDATA%\dlm\downloads`。
   备选：`%USERPROFILE%\Downloads\dlm`（用户更容易找到，但仍与浏览器下载混在一起）。
2. **已有的 Downloads 里的历史文件要不要搬？** 我建议**不搬**：
   搬文件是破坏性动作，而且队列里记的是名字不是绝对路径，
   搬了之后旧任务点「打开位置」会指错。新目录只影响**新任务**。

## 六、本轮结论

- 抽屉：**半截**（选中/高亮有，抽屉没画），数据基本齐，不动内核
- 统一目录：三处默认值不同 + `settings.out_dir` 是死代码
- 快速访问：后端全通，UI 零入口
- 任务同步：队列任务**已经同步**，缺的是带 Cookie / HLS 的直连任务
- 另有两处「界面在说谎」：速度列、剩余列恒为 `—`

**未改任何代码**，等用户确认目录方案与批次后动手。
