# 2026-11-27 浏览器下载不同步 —— 修复实测

用户原话：「浏览器插件下载的没有同步在桌面端软件显示」。

## 复现方法（修复前后各跑一次，同一个脚本）

1. 起 `dlm-gui`，队列为空，带 `--endpoint <dir>/endpoint.json --token devtok`
2. 写一份 native-host 配置，`gui_endpoint` 指向上面那个端点文件
3. 用原生消息协议（4 字节小端长度 + JSON）给 `dlm-native-host.exe` 各发一次 `download`：
   - A：不带 cookie
   - B：带 cookie（`sid=NEEDLE-COOKIE-4242`）
4. 每次之后用 `GET /api/tasks?t=devtok` 查队列
5. 最后读 `queue.json` 与 `secrets/*.bin`，搜明文

## 修复前（0.7.3 / `d75a8bb8`）

| 输入 | 宿主返回 | 桌面端队列 |
|---|---|---|
| A 不带 cookie | `mode: queue` | `['a.bin']` |
| B 带 cookie | `mode: direct` | 仍是 `['a.bin']`，**b.bin 不在** |

原因：`host.rs` 的分流条件是 `cookie.is_none() && !hls` 才走队列；带 cookie 的下载
被送到「直连」—— 起一个独立 `dlm.exe`，**不带 `--queue`**，GUI 完全不知道它存在。

## 修复后（步骤 1 + 步骤 2）

| 输入 | 宿主返回 | 桌面端队列 |
|---|---|---|
| A 不带 cookie | `mode: queue`，无 `reason` | `['a.bin', 'b.bin']` |
| B 带 cookie | **`mode: queue`**，无 `reason` | 同上 |

- `queue.json` 里含 `needs_secret`，**不含** `NEEDLE-COOKIE-4242`
- `secrets/1795766472968-2.bin` 存在，**246 字节**，其内也搜不到明文

## 回归用例

| 用例 | 钉的是 |
|---|---|
| `host::tests::a_cookie_download_goes_into_the_queue_with_its_cookie` | 带 cookie ⇒ `mode=queue`，且**请求正文里真的有 cookie** |
| `host::tests::a_direct_download_says_why_it_is_not_in_the_window` | 直连必须带 `reason`；进了队列就不许有 |
| `host::tests::host_keeps_hls_downloads_off_the_queue_endpoint` | HLS 仍不进队列（改写自旧用例，见下） |
| `gui::secrets::tests::the_file_on_disk_never_contains_the_plaintext` | 密文里搜不到明文 |
| `gui::tests::a_secret_task_passes_a_switch_but_never_the_value` | argv 里只有 `--cookie-stdin`，绝无凭证 |
| `integration::gui_encrypts_a_browser_cookie_instead_of_writing_it_plain` | 端到端：密文落盘、队列无明文、`needs_secret=true` |

全部做过变异验证（把修复注回去确认变红）。

## 一个旧用例曾经把 bug 当成规格

`host_keeps_cookie_downloads_on_the_direct_path` 断言「带 Cookie 必须直连，
且不许碰队列端点」—— 它保护的正是这次要修的行为。规矩本身没错，对象错了：
现在改名为 `host_keeps_hls_downloads_off_the_queue_endpoint`，保留同一个探针，换成 HLS。

> 教训：用例既能钉住正确行为，也能把错误行为固化下来。改行为时，先找出那条
> 「正在为你反对的事情站岗」的用例，改写它并在提交信息里说明，别偷偷删掉。

## 修复过程中踩到的两个测试坑

1. **桩线程不许 `join`**：HLS 用例根本不会去连那个桩，`join` 就是死锁
   （表现是 cargo test 挂住、没有任何输出）。
2. **`queue.json` 是延迟落盘的**：刚建完任务就读，会稳定读到 `os error 2`。
   要么轮询等文件出现，要么用未来的 `start_at` 钉住任务再断言。
