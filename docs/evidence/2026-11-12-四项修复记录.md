## E18：设置项 `connections` / `max_speed` 透传

### 改了什么

| 位置 | 之前 | 现在 |
|---|---|---|
| `gui/mod.rs` | `let per_host = 8usize;` 硬编码 | `RuntimeTuning::from_settings(Settings::load(...))` |
| `gui/runner.rs::child_args` | 不传 `--connections` / `--max-speed` | 两者都传 |
| `gui/runner.rs::connections_per_task` | 返回 `DEFAULT_CONNECTIONS` | 读 `tuning.connections` |
| `gui/app/settings_ui.rs` | 保存后只应用剪贴板开关 | 保存后发 `Ticket::ApplyRuntime`，**立刻生效** |
| `gui/mod.rs` | — | 新增 `RuntimeTuning` + `Ticket::ApplyRuntime` |

### 关键设计点

1. **一个来源**：`connections_per_task`（host 预算用）与 `child_args`（传给子进程）
   读**同一个** `tuning.connections`。如果两处读不同的数，就会出现「预算按 8 算、
   实际开 16 条」，每 host 上限形同虚设。
2. **立刻生效**：`ApplyRuntime` 在 runner 里就地替换 `tuning` 与 `gate.per_host`，
   下一轮 `tick` 派发时就用新值。不发这一条的话，用户改完设置得重启程序。
3. **不动已占用量**：`HostGate::set_per_host` 只换上限，不清 `usage` / `per_task` ——
   已占的连接是真实存在的，清掉会让归还算错。改设置不该把正在下的任务踢掉。
4. **夹下界 1**：手改 JSON 写成 `connections: 0` 会夹到 1（`--connections 0` 是参数错误）。

### 实测证据（真子进程 argv）

设置 `connections=16`、`max_speed_kib=2048`，起 headless GUI 加任务，读真实命令行：

```
"C:\Users\ROG\AppData\Local\dlm\bin\dlm.exe" --url http://127.0.0.1:8733/big.bin \
  --out-dir ...\out --out-name big.bin --quiet \
  --connections 16 --max-speed 2097152
```

`--connections 16` 与 `--max-speed 2097152`（= 2048 KiB/s）都在。
**修复前这里恒为 8 且没有 `--max-speed`。**

### 新增判据（2 条）

- `e18_connections_and_speed_reach_the_child_argv`
- `e18_runtime_tuning_projects_settings_and_keeps_one_source_of_truth`

| `gui/app/mod.rs` | 两个字段 `clipboard_hit` / `clipboard_dismissed`；工具条下方挂提示条 |
| `gui/app/theme.rs` | `CLIPBOARD_HINT_H = 32.0` |

### 语义决定：提示，不自动下载

IDM 那个勾选框是「监视…**并自动开始下载**」。dlm 只提示，理由：

1. 用户复制链接，绝大多数时候是要**发给别人**，不是要下载。
2. 剪贴板里可能有不该下的东西（内部链接、付费资源直链）。

提示条长这样：`剪贴板  file.zip            [下载] [忽略]`
点「下载」才投递；点「忽略」记进 `clipboard_dismissed`，同一条不再弹。

### 新增判据（2 条）

- `short_name_prefers_the_last_segment_when_it_looks_like_a_file`
- `short_name_falls_back_to_the_host_when_there_is_no_file_segment`

## 顺手修掉的一个测试竞态（真实 bug，不是我的改动引起）

跑门禁时 `hls_downloads_master_playlist_segments_in_order` 偶发失败，
报「HLS 清单返回 HTTP 404」。单跑必过、并发跑偶尔红。

**根因**在测试桩 `hls_stub`（`tests/integration.rs`）：

```rust
listener.set_nonblocking(true);   // listener 非阻塞
...
Ok((mut stream, _)) => {
    let mut buf = [0u8; 4096];
    let _ = stream.read(&mut buf);   // ← 错误被吞，buf 可能是全零
```

Windows 上非阻塞 listener `accept` 出来的 socket **继承非阻塞标志**，
`read` 可能立刻返回 `WouldBlock`；错误被 `let _` 吞掉后 `buf` 仍是全零
⇒ path 解析成空串 ⇒ 落到 404 分支。请求字节到得晚一点点就会踩中。

**修法**：显式 `set_nonblocking(false)`，并循环读到请求头结束（`\r\n\r\n`）
或 EOF，不再假设一次 read 拿全。

**验证**：单跑 8/8 通过；随后完整门禁 `integration 121 passed`。

> 这条值得记：它是**测试基础设施**的 bug，会让人误以为产品有 404 问题。
> 以前没暴露是因为时序刚好总是够。加测试跑得更久之后才浮出来。

## 直连重投落点问题 —— **已修（A 方案，2026-11-12 用户裁定）**

### 问题（当时发现）

实测直连重投时发现：**重投的落点可能与原任务不同，于是续不上**。

宿主配置里 `gui_endpoint` 可达时，重投会先走 `try_queue`，被队列接走
⇒ 落到**队列的 `out_dir`**，而不是原任务所在的目录。那里没有 `.dlm.json`，
所以从 0 开始下。实测：原任务 `out2\resumable.bin` 有 8 MB 半截，
重投却下到 `out\resumable.bin` 且「全长 41943040 B，落盘 41943040 B」。

三个候选方案：A（带原 `out_dir`）、B（强制直连）、C（改文案）。

### 裁定与实现：A

用户选 A。**A 的实际实现与 B 收敛成同一件事**，原因值得记下来：

直连任务的落点从来不是参数，而是宿主的 `config.download_dir`（固定值），
断点文件 `<名字>.dlm.json` 就在那里。而队列的落点是 `dlm-gui --out-dir`，
是**另一个目录**，且队列的 `/api/add` 根本不接受 `out_dir`。

所以「重投时带上原落点」在实现上就等于「重投必须强制直连、不许走队列」。
A 与 B 不是两个选项，而是同一个修法的两种描述 —— 这一点在裁定前没说清，
现在记在这里。

### 改动

| 位置 | 改动 |
|---|---|
| `host.rs` | `download` 拆成两层：`download`（按规则分流，可能进队列）+ `download_direct`（无条件直连） |
| `host.rs` | `resume` 的直连分支改调 `download_direct`，**跳过 `try_queue`** |

拆成两个函数而不是加一个 `bool` 参数：两种意图（「按规则分流」vs「就要直连」）
在调用点一眼能分开，比 `download(v, true)` 好读。

### 代价（已接受）

重投绕过队列的限流与配额。可以接受：直连任务本来就走这条路
（带 Cookie 的下载一直是直连），重投保持同一条路反而更一致。

### 判据（新增 1 条）

`e16_redelivery_skips_the_queue_even_when_it_is_reachable`

构造一个**可达**的队列桩（会返回 `{"ok":true,"id":"q-9"}`），然后断言重投
**没有**落到队列上 —— 回执不是 `mode:queue`、没有 `id`。
如果代码还在走队列，回执就会是 `mode:queue` + `id:q-9`，断言当场红。

### 实测证据（端到端）

20 MB 文件，先 `--max-bytes 8388608` 造 8 MB 半截 + 断点，
再经宿主 `op:resume` 重投：

```
回执 {"mode":"redeliver","op":"accepted","job":"1794462006-1",...}
续传输出：100.0%  20.0 MiB/20.0 MiB  dup 0.0%  用时 54 ms
final = 20971520 bytes，sha256 与源一致，断点文件自动删除
```

**`dup 0.0%` 是续传成立的关键证据**（没有重下任何已确认字节）；
**54 ms 对比全量 493 ms** 也说明它没有从头来。
