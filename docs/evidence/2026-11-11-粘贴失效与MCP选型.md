# 桌面端不能粘贴 URL（E17）与 MCP/CLI 选型裁定

**记录时间**：2026-11-11，用户实测首个测试版后反馈。
**状态**：E17 已定位到根因，**未修**；MCP/CLI 已裁定，**本轮不做**。

## 一、E17：桌面端粘贴不了 URL

**现象**：新建任务弹窗里，URL 输入框无法粘贴（Ctrl+V 无反应）。

### 根因（已确认，不是推断）

`Cargo.toml` 这一行：

```toml
eframe = { version = "0.37", default-features = false, features = ["glow", "default_fonts"] }
```

写了 `default-features = false`，而 `features` 列表里**没有 `clipboard`**。

依赖链是三层，任何一层断掉粘贴就静默失效：

| 层 | 事实 | 来源 |
|---|---|---|
| `eframe` | `clipboard = ["egui-winit/clipboard"]`，且它**在 default 里**（和 `accesskit`/`default_fonts`/`links`/`system_fonts` 一起） | `eframe-0.37.0/Cargo.toml` |
| `egui-winit` | `clipboard = ["arboard", "bytemuck", "smithay-clipboard"]` | `egui-winit-0.37.0/Cargo.toml` |
| 产物 | **`Cargo.lock` 里没有 `arboard`** —— 剪贴板后端根本没被编译进二进制 | `grep Cargo.lock` |

所以 Ctrl+V 时没有任何后端可以调用，egui 收不到粘贴事件，输入框保持为空。
这不是 egui 的 bug，也不是键盘事件被吞 —— **能力压根没编进来**。

### 同一个缺口还影响什么

- 右键菜单的「剪切 / 复制 / 粘贴」
- 选中文字后 Ctrl+C 复制出去
- 任何依赖 `egui::Context::copy_text` / `paste` 的路径

也就是说「复制粘贴网址」两个方向都是坏的，只是用户先撞上了粘贴。

### 修复（一行，未实施）

```toml
eframe = { version = "0.37", default-features = false, features = ["glow", "default_fonts", "clipboard"] }
```

代价评估：

- 新增依赖 `arboard`（Windows 上还带 `clipboard-win`），预计二进制约 +200–400 KB。
  当前 `dlm-gui.exe` 10.99 MB，占比很小。
- **不影响任何判据方向**，不改测试，只加一个 feature。门禁数字不变。
- 需要重新打包（二进制会变，sha256 会变）。

### 验证方法（修完必须实测，不许只看编译通过）

1. `cargo build --release --bins` 后 `Select-String Cargo.lock -Pattern 'arboard'` 应能查到。
2. 起窗口 → 新建任务 → 在外部复制一个 URL → 弹窗里 Ctrl+V → **输入框里出现文本**。
3. 反向：选中输入框里的文字 Ctrl+C → 粘到记事本 → 内容一致。
4. 右键菜单里「粘贴」也应可用。

**注意**：这条只能靠真窗口实测。`egui_kittest` 盖不到剪贴板（errata E11），
所以不要用测试断言假装验证过。

## 二、MCP 还是 CLI：选 CLI（而且它已经存在）

### 先说结论

**「加 CLI」这件事不用做 —— `dlm.exe` 就是完整的 CLI，已经随包发布。**
所以真正的问题只剩「要不要加 MCP」，我的判断是：**现在不加**。

### CLI 现状（实测 `dlm.exe --help`）

AI 要的「多线程下载」能力，CLI 一个不缺：

| 需求 | 现成参数 |
|---|---|
| 多线程 | `--connections <N>`（默认 8，至少 1） |
| 限速 | `--max-speed <BYTES_PER_SEC>`（0 = 不限） |
| 分段可控 | `--max-bytes <BYTES>`（到量即停**并保留断点**） |
| 断点续传 | 默认行为；同名目标 + `.dlm.json` 存在即续 |
| 校验 | `--sha256 <HEX>` |
| HLS | `--hls` |
| 完成后动作 | `--on-complete open \| run:<exe> \| shutdown:<秒>` |
| 试运行 | `--no-start`（只打摘要，不发请求） |
| 静默 | `--quiet`（只留最终摘要） |
| 认证 | `--cookie` / `--cookie-stdin` / `--user` / `--password` |

**退出码已经是契约**（`src/main.rs`）：`0` 成功、`2` 参数错、`3` 达到字节预算
（断点保留，再跑即续）、其余非零为下载失败。这对 Agent 编排已经够用 ——
`--max-bytes` + 退出码 3 + 重跑 = 天然的分块可控下载。

### 为什么现在不加 MCP

1. **MCP 不提供新能力**。它只能包一层去 shell out 调 `dlm.exe`，引擎侧一行都不用改。
   先做 MCP 等于把一个还没被真实使用场景压过的 CLI 契约提前固化。
2. **多一个常驻进程就多一个故障面**。MCP server 要长活、要 JSON-RPC、
   要处理 stdio 生命周期。现在已经有 `dlm-native-host` 在跑，
   再加一个常驻件会让「到底哪个进程挂了」变难查 —— 这个项目在
   「点了没反应」上已经踩过三次坑（见 `2026-11-11-extension-ball-fixes.md`）。
3. **Agent 今天就能用**。任何能执行 shell 的 Agent 直接调 `dlm.exe` 即可，
   不需要 MCP。等真的出现「Agent 反复拼错参数」「需要结构化返回值」这类具体痛点，
   再上 MCP 才有依据。
4. **CLI 契约还没写成文档**。参数和退出码目前只活在 `--help` 和源码注释里。
   MCP 的 tool schema 应该是这份契约的**投影**，而不是反过来定义它。

### 将来要做时的顺序（记下来，别临时拍脑袋）

1. 先写 `docs/specs/…-cli-contract.md`：参数、退出码、断点语义、
   哪些组合互斥（`--data-file` 与 `--max-bytes`/`--hls` 互斥等）。
2. 补几条**进程级**集成测试钉退出码（部分已有，如
   `the_binary_stops_at_the_byte_budget_and_resumes_to_completion`）。
3. 再写 MCP server，作为**薄适配层**：每个 tool 一次 `dlm.exe` 调用，
   把退出码映射成结构化结果，不做任何自己的下载逻辑。
4. MCP 里要暴露的 tool 大概是：`download`（url/out_dir/connections/max_speed）、
   `download_status`（读 `.dlm.json`）、`resume`、`cancel`。
   **不要**在 MCP 层重实现续传判定 —— 那是 `resume.rs` 的活，重写就是两本账。

### 一句话

**CLI 已经是那个「更好的选择」，而且已经交付；MCP 是它将来的一层皮，等有真实痛点再包。**
