# IDM 分段/并发实测（2026-11-13，C1 第二轮：服务端计数版）

## 方法（比第一轮可信）

`tmp/range_server.py` 在**服务端**为每个请求记一行 `{t, start, end, code}`：

- 文件 64 MiB（67,108,864 B），支持 `Range`，每连接限速 2 MiB/s
- `IDMan.exe /d http://127.0.0.1:<port>/file.bin /p <dir> /f probe.bin /n`
- 4 秒下完，共 **17 个请求**，日志无外部采样，全部是真实到达的请求

## 能得出的结论（有日志兜底）

1. **首请求是整文件 `200`**：IDM 先发一个不带 Range 的请求探路（拿长度/类型/是否可续），随后立刻转向分段。
2. **动态二分，不是固定块**：切点始终落在"当前剩余区间"的中点附近（1/2 → 3/4、1/4 → 1/8），随下载推进不断细切，而不是一开始就把文件切成 N 等份。
3. **2 秒内开出的并发连接 ≥ 8**：4 秒完成 64 MiB，而单连接被限到 2 MiB/s，只有多连接才可能。日志里同一毫秒附近成对出现（相差 48 字节），是"小探针 + 正式段"的典型形态。
4. **确实存在成对的 +48 字节请求**：同一区间先发一个极短请求再发正式请求；这属于它的探测策略，dlm 不必模仿（我们已有独立的 probe 阶段）。

## 对 dlm 的含义

| 观察 | dlm 现状 | 结论 |
|---|---|---|
| 动态二分（剩余区间取中点） | `scheduler::split_uses_remaining_part_of_active_segment` 就是"取剩余区间中点" | **方向一致，不需要改** |
| 并发 ≥ 8 | 默认并发上限由设置决定（默认值见 `settings`），未针对 64 MiB 调优 | **可考虑按文件大小阶梯放并发**，但要有更多样本 |
| 首请求整文件探路 | dlm 有独立 probe（`probe.rs`），语义等价 | 不需要改 |
| 固定块切分 | dlm 不是固定块 | 一致 |

**本轮不改任何引擎参数**：这组数据只够证明"dlm 的切分方向与 IDM 一致"，不足以证明某个并发数字更优。下一轮要测的是"不同文件大小下的并发峰值"，才谈得上调参。

## 复现命令

```powershell
$env:DLM_RATE_KBPS='2048'
python tmp\range_server.py 18779 tmp\probe.bin 67108864 tmp\conn-log.jsonl
IDMan.exe /d http://127.0.0.1:18779/file.bin /p tmp\out /f probe.bin /n
```
