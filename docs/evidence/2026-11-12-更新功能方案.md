# 更新功能方案（2026-11-12，待裁定）

**来源**：用户要求「要有更新功能，像真正的软件一样，方便后续加新功能直接更新进去」，
并补充「网页插件和桌面端要联动更新」。

本文只梳理现状与方案，**未改代码**。

---

## 一、现状：更新功能是「半截」

### 已有的（比想象中多）

| 组件 | 位置 | 状态 |
|---|---|---|
| `UpdateView` 结构 | `gui/snapshot.rs` | ✅ 8 个字段：enabled/current/latest/available/url/notes/checked_at/error |
| 版本比较 | `gui/mod.rs:405` `version_is_newer` | ✅ 按点分数字比，有单测 |
| 检查逻辑 | `gui/mod.rs:409` `check_update` | ✅ 拉一个 JSON 清单，读 `version`/`url`/`notes` |
| 后台检查线程 | `gui/mod.rs:195-200` | ✅ 启动时若给了 `--update-url` 就异步查 |
| HTTP 接口 | `GET /api/update` | ✅ 返回 `UpdateView` |
| 扩展侧版本 | `manifest.version` + `data-dlm-version` | ✅ 但只用于显示 |

### 缺的（关键全缺）

| 缺什么 | 证据 |
|---|---|
| **UI 里根本不显示** | `gui/app/` 下 grep `update` 只命中 import 与字段定义，**没有任何渲染**。`App.update` 字段还挂着 `#[allow(dead_code)]` |
| **不能下载** | `check_update` 只读 `url` 字段放进 `UpdateView.url`，没有任何下载代码 |
| **不能安装** | 无 |
| **默认不检查** | `update_url` 默认 `None`（`bin/dlm-gui.rs:45`），不传 `--update-url` 就永远不查 |
| **扩展完全不参与** | 扩展没有检查更新的代码，也不上报自己的版本给桌面端比对 |

**一句话**：现在是「能查版本号，但既不告诉你，也不能装」。

## 二、核心难点：扩展不能自更新

这是方案里最关键的一条，必须先讲清楚。

**Chrome/Edge 的 MV3 扩展，未上架商店时无法自动更新。**

| 分发方式 | 能否自动更新 | 说明 |
|---|---|---|
| Chrome Web Store | ✅ 浏览器自动 | 要开发者账号 + 审核 + 上架 |
| 自建 update_url | ⚠️ 仅限**已安装的打包扩展**（.crx） | 需要企业策略或开发者模式装 crx；普通用户装不了 |
| **「加载已解压」**（现在的方式） | ❌ **绝对不能** | 浏览器不允许程序化修改已加载的解压扩展 |

现在扩展就是「加载已解压」，扩展 ID `fkebhmogekekphpcggaclfgpfmofhdjk` 靠 manifest 里的 `key` 固定。

**所以「联动更新」的现实含义只能是**：

> 桌面端发现扩展有新版本 → **提示用户**「扩展有新版本，需要手动重载」→
> 桌面端把新文件**准备好**（拷到 `%LOCALAPPDATA%\dlm\extension`）→
> 用户点「重新加载扩展」或重启浏览器。

做不到「点一下就自动换掉扩展」—— 这是浏览器的限制，不是我们的实现问题。

### 能做到的最好效果

1. 桌面端把新扩展文件**写到磁盘**（这一步能做）
2. 桌面端检测「磁盘上的扩展版本 ≠ 浏览器里正在跑的版本」
3. 弹出提示：「扩展已更新到 0.2.12，请到 chrome://extensions 点『重新加载』」
4. 提供「打开扩展管理页」按钮（`chrome://extensions` 可以用 shell 打开）

这样用户只需点两下，而不是自己找文件、自己拷。

## 三、方案：三个版本号 + 一个更新器

### 版本模型

现在有两个独立版本号，容易混：

| 版本 | 现在 | 含义 |
|---|---|---|
| 内核 `0.1.0` | `Cargo.toml` | `dlm.exe` / `dlm-gui.exe` / `dlm-native-host.exe` |
| 扩展 `0.2.11` | `manifest.json` | 浏览器扩展 |

**建议增加第三个：发行版版本（release）**，例如 `1.0.0`。
它代表「这一整套一起发出去的组合」，清单里记录两个子版本：

```json
{
  "release": "1.0.0",
  "core": "0.1.0",
  "extension": "0.2.12",
  "url": "https://…/dlm-1.0.0-win-x64.zip",
  "sha256": "…",
  "notes": "修了粘贴、加了继续按钮…",
  "min_core": "0.1.0"
}
```

理由：用户感知的是「这个软件更新了」，不是「内核 0.1.0 变 0.1.1」。
两个子版本号是内部实现细节，放在清单里给更新器判断用。

### 更新器要做什么

```
检查清单 → 比对 release → 有新版则提示 → 用户确认 → 下载 zip
→ 校验 sha256 → 解压到临时目录 → 替换 exe → 提示重启
→ 扩展文件同时拷到位 → 提示重载扩展
```

### 关键设计决定

| 问题 | 建议 | 理由 |
|---|---|---|
| 谁来做更新？ | **独立的小程序 `dlm-updater.exe`** | 正在运行的 `dlm-gui.exe` 不能覆盖自己（Windows 文件占用）。独立进程可以 |
| 什么时候替换？ | 用户点「重启并更新」→ 启动 updater → 退出 gui → updater 替换 → 重启 gui | 避免「更新到一半程序还在跑」 |
| 校验 | **必须校验 sha256** | 下载的东西要装进 Program Files，不校验等于任意代码执行 |
| 失败怎么办 | 保留旧版本，回滚 | 解压到新目录成功后再切换，不要原地覆盖 |
| 是否自动检查 | 启动后延迟检查（比如 10 秒），**不阻塞启动** | 现在启动已经 573ms 超目标（E15），不能再加同步网络请求 |
| 是否自动安装 | **不自动**，必须用户点确认 | 装软件到 Program Files 是敏感动作 |

### 目录与权限

这跟上一份《安装位置与下载目录方案》强耦合：

- 装在 `E:\Program Files\dlm` ⇒ 更新时要写该目录 ⇒ **要 UAC**
- 装在 `E:\dlm` ⇒ 免管理员，更新可以静默替换

**这是个权衡**：正式安装位置（Program Files）换来每次更新要 UAC 一次。
Windows 上很多软件就是这样（如 VS Code 的用户版 vs 系统版）。

建议：**默认 `E:\Program Files\dlm`，但更新器支持提权**；
如果用户选了免管理员的 `E:\dlm`，更新就完全静默。

## 四、联动更新的具体流程

```
1. dlm-gui 启动
2. 延迟 10s 后台 GET 更新清单
3. 比对：
   - release 有新版？
   - 本地磁盘扩展版本 vs 浏览器里跑的版本？
4. 有任一不符 → 工具条/状态栏出现「有更新」标记
5. 用户点开 → 抽屉式面板显示：
   「桌面端 0.1.0 → 0.1.1」
   「扩展 0.2.11 → 0.2.12（需要手动重载）」
   [立即更新]  [稍后]
6. 点「立即更新」→ 下载 zip → 校验 → 启动 updater → 退出
7. updater 替换 exe + 拷扩展 → 重启 gui
8. gui 启动后检测：磁盘扩展版本 0.2.12 ≠ 浏览器版本 0.2.11
   → 提示「扩展已就绪，请到 chrome://extensions 点重新加载」
   → 按钮「打开扩展管理页」
```

### 怎么知道「浏览器里跑的是哪个版本」

两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 扩展启动时通过 Native Messaging 上报 `manifest.version`，宿主转给 GUI | 小；已有通道，加一个字段 |
| B | 只比对磁盘文件版本，不管浏览器 | 最小；但无法知道用户有没有真的重载 |

**建议 A**：扩展每次连上宿主时发 `{op:"hello", ext_version:"0.2.12"}`，
宿主回执里带上 `core_version`。这样 GUI 能同时知道两边的真实版本。

顺带好处：现在 `popup.js:88` 显示的「宿主 ok」就能变成「宿主 0.1.0 · 扩展 0.2.12」。

## 六、还需要你定的

1. **更新清单放哪？** 需要一台能公网访问的地方（GitHub Releases / 自己的服务器 / 对象存储）。
   **这一条不解决，更新功能没法真正工作**——本地测试可以，实际发布必须有 URL。
2. **要不要自动检查？** 我建议默认开（延迟 10 秒、失败静默），可在设置里关。
3. **扩展上不上商店？** 上架 Chrome Web Store 才能真自动更新扩展，
   但要开发者账号（$5）+ 审核 + 每次更新走审核。
   不上架就永远是「提示用户手动重载」。

---

## 七、结论

- 更新功能现在**只有版本比较的骨架**，UI 零显示、不能下载、不能安装
- 扩展**不可能自更新**（加载已解压的硬限制），只能「桌面端准备好文件 + 提示用户重载」
- 建议引入**发行版版本号**统一两边，加一个独立 `dlm-updater.exe`
- **必须校验 sha256**，必须有回滚
- 与「安装位置」方案强耦合：装 Program Files ⇒ 更新要 UAC

**未改任何代码。** 等用户定第六节那三件事。
