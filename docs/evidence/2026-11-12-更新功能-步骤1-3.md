## 一、步骤 1：清单格式（`latest.json` 三个版本号）

### 改了什么

| 位置 | 改动 |
|---|---|
| `gui::RELEASE` | 新增常量，本机**发行版**版本（用户感知的那个号），更新判断只看它 |
| `gui::DEFAULT_UPDATE_URL` | 默认源 `https://raw.githubusercontent.com/Samuel666198/dlm/main/latest.json` |
| `gui::UPDATE_CHECK_DELAY_SECS` | `10`：自动检查等冷启动过去再查 |
| `parse_manifest` | 新格式 + 老格式都认；老格式的 `version`/`latest` 当作 `release` |
| `UpdateView` | 加 `core_current` / `core` / `extension` / `extension_running` / `sha256` / `size` / `min_core` / `published_at` / `installable` / `blocked` |
| `Settings` | 加 `auto_check_update`（**默认 true**），`gui::run` 真的读它 |
| `bin/dlm-gui.rs` | 默认 `update_url = DEFAULT_UPDATE_URL`；新增 `--no-update-check`；显式 `--update-url` ⇒ 延迟 0 |
| `packaging/build-package.ps1` | 打包时**顺手产出 `latest.json`**（sha256/size 直接取刚打出来的 zip），新增 `-Release` / `-Notes` / `-MinCore` / `-Url` |

### 一个设计决定：`available` 与 `installable` 分开

装进安装目录的东西必须校验摘要。但「有新版」和「能自动装」是两件事：

| 字段 | 含义 |
|---|---|
| `available` | 清单里确实有更新的发行版（**事实**） |
| `installable` | 能自动装（有 `sha256`、满足 `min_core`） |
| `blocked` | 装不了的原因，给人看 |

混成一个布尔会出的事：清单缺摘要 ⇒ 界面显示「没有更新」⇒ 用户永远等不到提示。
现在的语义是「有新版，但只能手动装」，原因是清单内容不完整 —— 这两句都在面板上。

## 二、步骤 2：更新提示界面（原来零显示）

| 位置 | 显示什么 |
|---|---|
| 状态栏右侧 | 有新版 ⇒ 可点的 `有新版 1.0.0`（强调色）；检查失败 ⇒ `更新检查失败`；检查中 ⇒ `检查更新…` |
| 更新面板 | 发行版 `0.1.0 → 1.0.0`、桌面端 `0.1.0 → 0.1.1`、扩展 `0.2.12`（+ 浏览器里跑的是哪个版本）、发布说明、不能自动装的原因、清单地址 |
| 面板按钮 | 立即检查（后台线程，结果走通道回 UI 线程）、打开发布页、关闭 |

新增文件 `src/gui/app/update_ui.rs`。`App.update` 上那个 `#[allow(dead_code)]` 删掉了 ——
数据终于接到了屏幕上。

**一个细节**：手动检查的结果用 `mpsc` 通道回 UI 线程，不是「线程直接写槽 + 置个布尔」。
秒粒度的 `checked_at` 分不清「这次查完」和「启动那次查完」，界面会一直挂着「检查中」。

**另一个细节**：`install_update_view()` 换视图时**保留** `extension_running`。
那个字段来自扩展的实时上报，不是清单里的东西；整份覆盖会让它每次检查后凭空丢掉。

## 三、步骤 3：ping 双向带版本号

| 方向 | 之前 | 现在 |
|---|---|---|
| 扩展 → 宿主 | `{"op":"ping"}` | `{"op":"ping","ext_version":"0.2.12"}` |
| 宿主 → 扩展 | `{op,host,version}` | 加 `core_version`（同一件东西的明确名字，清单里 `core` 指的就是它）+ 原样回显 `ext_version` |
| 宿主 → 桌面端 | 无 | `POST /api/ext-hello?t=…` body `{"version":"0.2.12"}` |

- 宿主侧：**同一版本只转一次**（扩展每次连宿主都 ping，每 ping 一个 HTTP 请求是白花钱）、
  **失败静默**（GUI 没起来不能影响下载）、2 秒超时。
- 桌面端侧：`POST /api/ext-hello` 把版本写进 `UpdateView.extension_running`。
- 扩展侧：`popup.js` 状态从「宿主 0.1.0」变成「**宿主 0.1.0 · 扩展 0.2.12**」，
  两个号一起显示才看得出「桌面端和扩展是不是同一对」。
- 扩展版本 **0.2.11 → 0.2.12**，`background-0.2.12.js`（文件名带版本号是为了绕 SW 缓存），
  已同步到 `%LOCALAPPDATA%\dlm\extension` 并清掉旧的 `background-0.2.11.js`。

> 用户仍需在 `chrome://extensions` 点一次「重新加载」，扩展才会真的跑 0.2.12 ——
> 这正是步骤 5 要做的「请重载」提示所服务的那件事。

### 一个测试纪律：门禁里不许有真实外网请求

更新检查会在启动 10 秒后请求 `raw.githubusercontent.com`。集成测试有八九处起 GUI，
漏一处就会在门禁里真发一次请求 —— 那种测试是假绿：机器断网就变红。

做法：`gates.ps1` 设 `DLM_NO_UPDATE_CHECK=1`，子进程继承，一处设置覆盖全部用例；
唯一在测更新检查的那条用例显式 `.env_remove("DLM_NO_UPDATE_CHECK")` 并传 `--update-url`
（显式给了地址就不等那十秒）。

### 步骤 4 已经想清楚的部分（省下一轮的时间）

- 安装目录**不能硬编码**：现在装的是 `%LOCALAPPDATA%\dlm\bin`（`install.ps1` 第 9 行），
  而《安装位置与下载目录方案》里裁定的 `E:\Program Files\dlm` **还没实现**。
  updater 应该接 `--install-dir`（由 `dlm-gui` 传自己的 exe 目录），落地时再改安装脚本。
- 解压可以复用打包侧的 `Compress-Archive` / `Expand-Archive`，不引入 `zip` 依赖。
- 替换必须先 `rename` 旧的再写新的，失败全部回滚 —— 正在跑的 `dlm-gui.exe` 不能覆盖自己，
  所以一定是「退出 → updater 替换 → 重启」。
- 摘要校验用已有的 `sha2` 依赖，不新增。
