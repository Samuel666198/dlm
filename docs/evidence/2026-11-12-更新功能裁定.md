# 更新功能：裁定与实施要点（2026-11-12）

**来源**：用户在《更新功能方案》之后给出三条裁定。本文记录裁定、补上由此产生的
新缺口，并给出可执行的实施要点。**未改代码。**

---

## 一、用户裁定

| 问题 | 裁定 |
|---|---|
| 更新清单放哪 | **GitHub，自动检查** |
| 要不要自动检查 | 是（默认开） |
| 扩展上不上商店 | **不上商店**，但要参与更新（"可以开扩展"） |

---

## 二、裁定带来的一个**新缺口**

「放 GitHub 自动检查」需要两样东西，现在都还没有：

| 需要 | 现状 |
|---|---|
| 一个 GitHub 仓库 | **项目无远程、从未 push**（交接文件明写「分支 `sdd/dlm-kernel`，无远程、未 push」） |
| 仓库里有一个稳定的清单 URL | 无 |

也就是说：**更新功能的落地前提是先把项目推到一个 GitHub 仓库**。
在那之前，只能本地测（`--update-url` 指本地文件/本地 HTTP），不能真的自动检查。

> 按硬纪律，`git push` 必须先取得用户点头。这条不解决，更新功能只能做一半。

---

## 三、GitHub 方案的具体设计

### 用 Releases + 仓库内的清单，不用 API

| 用途 | URL 形态 | 理由 |
|---|---|---|
| 检查更新 | `https://raw.githubusercontent.com/<owner>/<repo>/main/latest.json` | 不消耗 GitHub API 配额（未认证 API 只有 60 次/小时）；raw 走 CDN，几分钟缓存对更新检查无影响 |
| 下载安装包 | `https://github.com/<owner>/<repo>/releases/download/<tag>/dlm-<ver>-win-x64.zip` | Release asset，稳定、可断点续传（正好用我们自己的内核能力） |
| 校验 | 清单里的 `sha256` | 必须 |

**为什么不用 `api.github.com/repos/.../releases/latest`**：
未认证 60 次/小时，用户多开几次或调试时容易打满；raw URL 没有这个限制。

### 清单格式（`latest.json`，放仓库根）

```json
{
  "release": "1.0.0",
  "core": "0.1.0",
  "extension": "0.2.12",
  "url": "https://github.com/<owner>/<repo>/releases/download/v1.0.0/dlm-1.0.0-win-x64.zip",
  "sha256": "<64 位十六进制>",
  "size": 9437323,
  "notes": "修了粘贴、加了继续按钮、设置真的生效了",
  "min_core": "0.1.0",
  "published_at": "2026-11-12T18:00:00Z"
}
```

三个版本号的作用：

| 字段 | 谁用 |
|---|---|
| `release` | 用户感知的「软件版本」；更新器据此判断要不要更新 |
| `core` | 桌面端（三个 exe）的实际版本，与 `Cargo.toml` 一致 |
| `extension` | 扩展版本，与 `manifest.json` 一致 |

**比对规则**：`release` 变新 ⇒ 提示更新。同时分别显示 `core` / `extension`
是否也变了 —— 这样用户知道「这次更新会不会连带换扩展」。

## 四、扩展联动：不上商店时的真实做法

扩展是「加载已解压」，浏览器**不允许**程序化替换。所以联动更新只能做到：

```
1. 桌面端发现清单里 extension 版本 > 本地磁盘版本
2. 下载 zip，解压后把新扩展文件写到 %LOCALAPPDATA%\dlm\extension
3. 记下「磁盘版本 0.2.12」
4. 扩展通过 Native Messaging 上报自己正在跑的 manifest.version（仍是 0.2.11）
5. 桌面端比对：磁盘 0.2.12 ≠ 运行中 0.2.11
   ⇒ 提示「扩展已就绪，请到 chrome://extensions 点『重新加载』」
   ⇒ 提供按钮「打开扩展管理页」
6. 用户点重新加载后，扩展上报 0.2.12 ⇒ 提示消失
```

**关键点：第 4 步的版本上报**。现在扩展连上宿主只发 `{op:"ping"}`，
回执里有 `host`/`version`。要扩成双向：

| 方向 | 现在 | 要加 |
|---|---|---|
| 扩展 → 宿主 | `{"op":"ping"}` | `{"op":"ping","ext_version":"0.2.12"}` |
| 宿主 → 扩展 | `{"op":"pong","host":"com.dlm.host","version":"0.1.0"}` | 加 `core_version`，语义更明确 |

这样桌面端能同时知道两边的真实版本，才能判断「用户到底重载了没有」。
顺带 `popup.js` 显示的「宿主 ok」可以变成「宿主 0.1.0 · 扩展 0.2.12」。

### 做不到的，明说

- ❌ 点一下按钮就换掉扩展（浏览器限制）
- ❌ 自动重载扩展（同上）
- ✅ 把文件准备好 + 告诉用户点哪里 + 验证是否真的重载了

## 五、实施顺序（依赖关系决定，不是偏好）

| 步 | 做什么 | 依赖 |
|---|---|---|
| **0** | **建 GitHub 仓库并 push** | 需要用户点头（硬纪律） |
| 1 | `latest.json` 格式 + 发布脚本自动生成（含 sha256） | 0 |
| 2 | 扩展现有 `check_update` 支持新清单格式（`release`/`core`/`extension`/`sha256`） | 1 |
| 3 | 更新提示 UI（现在零显示） | 2 |
| 4 | `ping` 双向带版本号 | 无（可并行） |
| 5 | `dlm-updater.exe`：下载 + 校验 + 解压 + 替换 + 回滚 | 1 |
| 6 | 扩展文件落地 + 「请重载」提示 + 打开扩展管理页 | 3、4 |

**第 0 步是硬前置**。没有仓库，1–6 都只能本地测。

## 六、仍需用户提供/确认

| # | 事项 | 为什么必须 |
|---|---|---|
| 1 | **GitHub 仓库地址**（`owner/repo`），以及是否授权 push | 更新源的前提；push 按纪律要点头 |
| 2 | 仓库公开还是私有 | **私有仓库的 raw URL 需要 token**，更新器就得处理凭据；公开仓库最简单 |
| 3 | 上一轮《安装位置》那三问（安装目录是否要 UAC、下载目录、数据目录） | 更新器要往安装目录写文件，装哪决定要不要提权 |

我按最小阻力推荐：

- **公开仓库**（私有要处理 token，复杂度陡增）
- 安装 `E:\Program Files\dlm`（正式安装，更新时 UAC 一次）
- 数据 `E:\ProgramData\dlm`
- 下载 `E:\dlm-downloads`

## 七、一句话结论

更新功能的**代码骨架已经有一半**（版本比较、清单解析、后台线程、HTTP 接口），
缺的是 UI、下载安装、以及扩展联动。

**但真正的卡点是第 0 步：项目还没有 GitHub 仓库。**
这件事不点头，剩下的都只能本地演练。
