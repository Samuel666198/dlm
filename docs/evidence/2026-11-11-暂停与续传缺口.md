# 暂停之后没有「继续」：三条投递路径的入口缺口（只读定位，未改代码）

**用户反馈（2026-11-11，真机）**：网页端插件已可正常使用，但**不能断点续传** ——
一个任务暂停之后，没有「继续」这个选项。

**一句话结论**：内核的续传能力是好的，**缺的是入口**。扩展面板里「进行中」的每一行
只有「停止」一个按钮，「最近」里那一行只有文字、一个按钮都没有；队列模式的任务扩展
根本看不见。三条投递路径各自断在不同地方，不是同一处坏了。

> 本文只记录读代码得出的定位结论。**没有跑过任何运行时验证**，所有「会怎样」都是
> 从实现推的，不是实测；落地修复前必须按文末「待验证」逐条证实。

| 项 | 值 |
|---|---|

## 一、内核这边是好的

续传的判据、断点文件、原子落盘都在，且被门禁钉着：

| 能力 | 位置 | 说明 |
|---|---|---|
| 断点判定 | `src/resume.rs` `decide` ①–⑥ | ①b 请求一致性 → ②最终 URL → ③ETag/Last-Modified → ④长度 → ⑤Range 支持 |
| 断点文件 | `state.rs::path_for` | `<目标文件>.dlm.json`，`state::save` 走 `.tmp` + rename 原子替换 |
| 周期落盘 | `engine.rs::save_if_due` + `consts::STATE_SAVE_MAX_INTERVAL_SECS = 5` | 有字节被确认、且距上次保存 ≥5 秒才写 |
| 最终落盘 | `engine.rs::finish` | 「成败都落」，失败那一支正是下次续传的依据 |
| 调度器播种 | `Scheduler::resume(total, min_seg, &done)` | 覆盖集原样喂回，已被 `scheduler` 用例钉住 |
| GUI 的继续 | `gui/runner.rs` `Ticket::Resume` | `Paused`/`Failed` → `Queued`，原生窗口工具条「继续」按钮可用 |

所以问题不在「能不能续」，在「用户按不到续」。

## 二、三条路径各断在哪

扩展投递有两条路，`host.rs::download` 按「有没有 Cookie / 是不是 HLS」分流；
再加上 GUI 自己的队列，一共三个入口。

### 路径 A：队列模式（无 Cookie 的公开直链）

`host.rs:190` —— `cookie.is_none() && !hls` 时走 `try_queue` → `POST /api/add`
→ 返回 `{"mode":"queue","id":...}`。

- **扩展侧**：`content.js:871` 收到 `mode === "queue"` 就把它塞进 `state.finished`，
  文案「已加入队列 X」。**这一行在 `renderFinished` 里只生成 `<span>`，没有任何按钮**
  （`content.js:519–537`）。
- **扩展够不到 GUI**：全仓 grep 过，`browser/extension/` 里**零处** `fetch` /
  `127.0.0.1` / `/api/`。扩展只会走 Native Messaging，不会说 HTTP。
- 而 GUI 的 `/api/resume`（`gui/http.rs:192`）与工具条「继续」都是好的 ——
  **能力在，只是扩展这一侧没有通道也没有按钮**。
- 结论：队列任务要续，目前只能回原生窗口里点。用户如果只开浏览器，就完全没有入口。

### 路径 B：直连模式（带 Cookie，或 HLS）

`host.rs:387` `cancel` → Windows 上直接 `taskkill /PID <pid> /F`。

- 这是**强杀**，不是优雅暂停：`engine::finish` 不会跑 ⇒ 最终断点不落盘，
  只能靠 5 秒周期保存兜住，**最多丢约 5 秒已确认进度**（丢了只是重下，不会写坏）。
- 回执文案是 `"已停止，断点保留"`（`host.rs:428`），断点确实还在，
  但「保留」这两个字对刚过去的 5 秒略微乐观，值得在文档里说清楚。
- 扩展收到 `job-done` + `canceled:true` → 落进「最近」，文案「已停止（断点保留）」
  （`content.js:528`）。**同样没有按钮**。
- 理论上重投同一个 URL 就能续（同名 → 同一个 `.dlm.json` → `resume::decide` 判 `Resume`），
  但**扩展没给重投入口**，用户得自己回去再点一次页面上的链接。
- 附加风险：`resume` 的 ①b 会逐字比 `url / referer / cookies / data_file / user`。
  重新点链接时 Cookie 是**重新采集**的，会话刷新过就会判 `Fresh` 从头下。
  也就是说「重投 = 续传」这条经验并不可靠，得实测。

### 路径 C：HLS

`src/hls.rs` 模块文档第 4 行写死了：**「失败保留半截文件，下次从头开始（不是断点续传）」**。

这是设计决定，不是 bug。但用户在扩展里看到的也是「停止」，停止后同样没有继续 ——
所以对 HLS 任务，**应该显式说明「不支持续传」**，而不是让用户以为能续。

## 三、顺带发现的两处措辞问题

1. **「暂停」其实是「强杀」**。`gui/runner.rs:119` 的 `Ticket::Pause` 也是 `child.kill()`，
   与扩展的 `taskkill /F` 同性质。界面上叫「暂停」，语义上是「中断并保留断点」。
   这不影响正确性，但影响用户预期 —— 他以为能无损接着跑，实际要重下最多 5 秒。
2. **`gui/app/list.rs:355` 的 `speed_text` 恒返回 `"—"`**，`TaskView` 没有速率字段。
   与本次问题无关，但同属「界面承诺了但没数据」的一类，一并记在这里。

## 四、修复方向（未实施，等确认）

按代价从小到大，三条独立可做：

| # | 做什么 | 落在哪 | 代价 |
|---|---|---|---|
| 1 | 「最近」里 `canceled` 的行加一个「继续」按钮，点击重投同一 `url + name + cookie` | `content.js` `renderFinished` + `runHostAction` | 小。但只对直连模式有效，且受 ①b 的 Cookie 比对影响 |
| 2 | 队列任务的「继续」：扩展 → 宿主 → `POST /api/resume` | 新增 `host.rs` 一个 op + `background` 一条转发 + 面板按钮 | 中。要新开一条宿主 HTTP 通道（`try_queue` 已有现成的 endpoint 读取与 client，可复用） |
| 3 | 让 `/api/add` 在「同 URL + 同名任务已存在且为 paused」时直接返回既有 id | `queue.rs::add` / `gui/http.rs` | 中。要定义「同名同 URL」的判定，且不能破坏现有去重语义 |

方向 1 最快见效，但方向 2 才是真正把队列续传接进浏览器 —— 建议 2 为主、1 作为直连兜底。

HLS 那一条不做修复，只做**文案**：面板里给 HLS 任务的停止结果加一句「HLS 不支持续传，需重新下载」。

## 五、待验证（修复前必须先证实，别信推断）

本轮全是读代码推的。下面每一条都要实测，不许拿合成输入当真实点击
（见 `2026-11-11-extension-ball-fixes.md` 的三轮误判复盘）：

1. 直连模式停止后，重投同一 URL 是否真的判 `Resume` 而不是 `Fresh`？
   要看 `dlm.exe` 的 stderr/日志里有没有「请求与断点不符：换了 Cookie」这类句子。
2. 强杀后 `.dlm.json` 的实际内容与目标文件长度是否自洽（周期保存到底存到哪一刻）？
3. 队列模式下 GUI 点「继续」能否真的把 paused 任务推回 running？现有用例
   （`queue::tests` 里只钉了 `running_becomes_paused_on_recovery`）没有覆盖 resume 这一支。
4. 扩展面板在「最近」里加按钮之后，站点拦截事件的场景是否仍然可点
   （必须走 `onWindowClick` 统一路由，不能挂元素级监听 —— 0.2.9 的教训）。
