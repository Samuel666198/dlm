## 2. 场景 B —— 48 MiB 限速（`/slow`）

- **用例名**：`scenario_b_throttled_splits_at_midpoints_and_respects_the_floor`
- **形状**：对端 `{base}/slow`（每块 64 KiB 之间 `setTimeout(200)` ⇒ 单条连接 ≈320 KiB/s），
  进程内 `engine::run`，`workers: 8`，`min_seg: MIN_SEGMENT_BYTES`，`verify_sha256: Some(expected_sha(48 MiB))`
- **尺寸没有缩**（**E28⑤** 的明令）：48 MiB 全尺寸。
- **它是判据①（限速档那一跑）与判据②的载体**：判据②在这里量的是"**劈分中点真的出现在线上**"
  —— 内部账说"我从 `mid` 把这条区间劈开了"不算数，必须有一条服务端亲手记下的 `Range` 就从 `mid` 开始；
  外加"`MIN_SEGMENT_BYTES` 这道下限从没被踩"与"劈点不落在父区间中点以左 / 上半截不超过父区间一半"两条中点算术。
- **实测数**（同一发跑了两次，两行原文都留）：

  ```
  SCENB 取证：用时 26.5688411s、Range 枪 54、连接 33、劈分 51、劈分到达最早 1698 ms / 最晚 24753 ms、
              父在飞时劈的 46 发（其中 2 s 之后 44 发）、引擎报 dup 10043421 B
  SCENB 取证：用时 26.4684096s、Range 枪 53、连接 28、劈分 48、劈分到达最早 1834 ms / 最晚 24885 ms、
              父在飞时劈的 48 发（其中 2 s 之后 41 发）、引擎报 dup 9928095 B
  ```
  两次 `cargo test` 分别 `finished in 30.34s` / `29.82s`。
- **首跑结果**：**先红后绿**。RED #1（原文）：

  ```
  Error: 劈点 37807744 之前线上没有任何一条从 25283840 开始的 Range ⇒ 这一劈不是从在飞的那一枪上劈下来的
  test result: FAILED. 0 passed; 1 failed; ...; finished in 29.59s
  ```
  ⇒ 这一发红的不是实现，**是我写错的判据**：`TraceStep::Dispatched/Tightened` 记进账的时刻是**派单**时刻，
  请求上线还要再过一次引擎→worker 的投递，所以"刚派出去、还没上线的区间被下一发 `Connected` 劈一刀"是合法形状。
  处置：把顺序义务收成"被劈的那条区间上过线"（universal）+ "父那一枪当时还没写完"（existential，
  按连接的响应序配对 `response_done`），并在用例文档里把这条实测教训写明。**没有放宽任何既有断言的方向。**
- **时长与 E28⑤ 对照**：本轮亲量 26.47 / 26.57 s（控制员那一跑 23967 ms）。同一档、同一形状，差 ~2 s 属对端节拍抖动，
  照实登记，不取悦任何一个数。
- **`dup` 那一格**：9,928,095 / 10,043,421 B ≈ **19.7% / 20.0% 的文件体量**，与控制员复量的 10,292,453 B（≈20%）同族
  ⇒ 就是 **E14③** 那笔"残余超读"（窗口被收紧的帽砍断、对端已经把字节写进 socket 的那一截），不是本轮的缺陷。

- **形状**：`ScriptedPeer`（`workers = 1`，`max_retries: Some(0)`），512 KiB，第 1 枪交出 100 000 B 后被拆线、

  只许给 `workers == 1` 或退化形状用 ⇒ 多 worker 那一档今天没人量。

### 3.2 本轮新加那一发：多 worker、真进程硬杀

- **用例名**：`scenario_c_real_process_kill_then_resume_does_not_redownload_covered_bytes`
- **形状**：node 对端 `{base}/slow`（48 MiB）+ **真 `dlm.exe` 子进程**、`--connections 8 --quiet`；
  杀点取**可观测量**（轮询断点文件，"覆盖字节第一次长到种子之上"那一拍就 `Child::kill()`
  = TerminateProcess，不给任何收尾机会），不是固定 `sleep`；然后**同一 URL、同一命令**再跑一遍等它退 0。
- **它是判据③在 8 连接 + 真被杀下的载体**。R11 把 §6.6 的承诺改成"任意时刻被杀都能续"，这一发就是那句的字面形状。
- **实测数（最终那一跑，`SCENC 取证` 原文）**：

  ```
  SCENC 取证：杀于 13.7616802s（覆盖集长到种子上方那一拍；覆盖集长到种子上方那一拍 13.7581067s）；
              断点覆盖 2 格 / 4430336 B；半截文件 48198464 B；第一个未覆盖字节 236032；
              第二轮 52 枪 / 交出 55392150 B / 落在覆盖集内 236032 B（其中试探那一枪 236032 B）；
              第二轮剔掉试探后最早起点 236032 B
  ```
  `finished in 39.60s`。推导量（都由上面这些实测数算出，不是另跑的）：
  - 第二轮**没有**重下断点说"已归我"的任何一个字节（试探那一枪之外 `dup = 0`）；
  - 这一档续传买到的重复字节减少量 = `4430336 − 236032 = 4194304 B`（= 48 MiB 的 **8.33%**）；
  - 第二轮该下的 = `50331648 − 4430336 = 45901312 B`，对端真交出 `55392150 B`
    ⇒ 超读 `9490838 B` = 该下量的 **20.7%**，与 §2 那 20% 同一族（**E14③**）；
  - `55392150 − 50331648 = 5060502 B`，即第二轮光是超读就交出了比"整份文件还多 10%"的字节。
- **首跑结果**：第一轮跑就绿，但**那一跑的结论不能算验收过**（详见下面 3.3），所以这里如实写成
  "形状到货即绿、判据第一次没有牙 ⇒ 改的是杀点前提，不是断言方向"。
- **牙用变异证**（§5 表 M-C1）：把第二轮换成 `--no-resume` ⇒ 实测红在
  `第二轮第 1 枪要走了断点文件说已归我的 4194304 B（交出去的那段 (25283840, 29478143)）`。

### 3.3 ⚠️ **E28⑫ 那一格：本轮量到了，而且量到两次**

第一次跑这一发时杀点上限取的是 12 s，实测原文：

```
SCENC 取证：杀于 12.0185487s（12 s 上限（断点没长出种子之外，E28⑫ 那一格）；覆盖集长到种子上方那一拍 未出现）；
            断点覆盖 1 格 / 236032 B；半截文件 47674176 B；第一个未覆盖字节 236032；
            第二轮 55 枪 / 交出 59700799 B / 落在覆盖集内 236032 B（其中试探那一枪 236032 B）
```
`finished in 39.68s`。那一跑**绿**，但绿的是一具空判据：断点里只有初始那一格种子（236 032 B），
"不许重下覆盖集内的字节"于是退化成"不许重下预读那一截"，而第二轮本来也不可能重下它。

**量到的事实**：
- 盘上已经落了两千多倍的字节（`47674176 B`），断点只承认 `236032 B`；
- **覆盖集长出第二格的时刻 = 13.758 ms 那一拍**（第二次跑测得 13.7581067 s），
  与"`/slow` 上一枪 = 一个 4 MiB 窗口 ≈ 13.1 s"对得上：`Progress` 不往 `done` 里加字节，
  只有**一枪收尾**才加 ⇒ 保存闸（`moved && last_save.elapsed() >= 5 s`）里那个 `moved`
  在限速对上要到第一枪完成才为真，于是"5 s 兜底"事实上被"必须有新字节确认"这条合取压住 —— 这正是 **E28⑫** 说的那件事；
- ⇒ **这一档续传买到的重复字节减少量的真实函数是**：`杀点 < ~13.8 s ⇒ 0 B`；`杀点 ≥ 那一拍 ⇒ 每确认一窗 4 194 304 B`
  （本轮那一跑只有 1 窗确认 ⇒ 8.33%）。**没有为了好看的数去调尺寸**（48 MiB 没动），
  只把杀点上限从 12 s 挪到 30 s，并加了一条"前提没成立就如实失败/登记"的写法。

**这条不算本轮缺陷**：`save_if_due` 的合取闸是 **T8 面**的既有形状，E28⑫ 明写"本轮不动"。

## 4. 场景 D —— 无 `Accept-Ranges` 退化

- **用例名**：`no_ranges_falls_back_to_single_worker_and_is_correct`（Task 8 落的，本轮**一字未改**）
- **它是判据④唯一的载体**：A 段走 node 的 `/noranges`（`workers: 4`，钉字节正确 + "四个 worker 都报了就绪、
  线上却只多出一条 Range" + 第一枪问的是起点最低的那段缝）；B 段走进程内 `Shot::IgnoresRange`（5 MiB > 一个窗口，
  钉"接缝首尾相接、互不重叠"）。
- **实测数**：**本轮未单独计时/重量这一发**。它在全量集成闸里跑到（`88 passed / 0 failed` 含它）。
  需要它自己的读数请单独跑 `cargo test --test integration no_ranges -- --nocapture`。
- ⚠ **48 MiB 这一格在 D 上今天造不出来**：`probe-server.mjs` 的 `/noranges` 分支把 body 硬夹在
  `Math.min(sendLen, 1024 * 1024)` ⇒ 那条路由**最多只能交 1 MiB**（既有用例文档已记这件事）。
  所以判据④的形状正确性量在 1 MiB（node）+ 5 MiB（进程内退化对端）上，**量不到 48 MiB**，
  这不是测试偷懒，是仪器上没有那个对端。

## 6. 偏差登记（量到的与文档承诺不符的地方）

3. **B 的 `dup` ≈ 20%**（9.93–10.04 MB / 48 MiB）＝ **E14③** 的残余超读，不是这一轮的缺陷；
   C 的第二轮超读 9.49 MB（该下量的 20.7%）同族。两处的措辞都按 **E14③** 批准的那一句读：

   判据③退化成空判据。⇒ 场景 C 的杀点前提写进了用例文档，且这一格的两个数（0 B 与 4 194 304 B）**都留在本文件里**，
