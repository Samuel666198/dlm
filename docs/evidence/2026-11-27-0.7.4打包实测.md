## 发布过程中撞到的两个网络故障（都不是代码问题）

1. **git 推送被重置**：`Recv failure: Connection was reset`，反复 3 次；
   `gh api` 走 api.github.com 正常。DNS 解析到 `57.155.223.240`，查 `gh api meta`
   确认它在 GitHub 官方 `57.155.223.240/28` 段里 —— 当时推断是 TLS 层间歇性干扰。

   **更正（用户 2026-11-27 说明）**：真实原因是**本机当时没开 VPN**。
   所以不是 GitHub 或链路本身的问题，也不是 TLS 被干扰 —— 是这台机器出网的姿势不对。
   这条更正很重要：按错误的推断走，会去折腾 SSH 通道、改 remote、甚至怀疑 DNS 投毒，
   而正确答案只是"把 VPN 打开"。**下次类似现象先问一句网络环境，再开始排查。**
2. **MCP 包下载被截断**：第一次实收 2,093,120 字节（声明 2,109,066），sha 自然对不上。
   带长度校验重下，第 2 次拿到完整体，哈希一致。**没有把截断当成"资产损坏"**。

## 一个未能定性的观察

改完版本号后第一次跑门禁，`lib` 那格报 `FAIL exit 101`，但当时输出被
`Select-Object -Last 14` 截断，失败用例名没留下来。随后单独跑 `cargo test --lib`
（带上门禁那几个环境变量）通过 582/582，再整跑门禁也全绿。

**没有把它当成"偶发"就过去。** 补测：带同一组环境变量连跑 `cargo test --lib` 4 次，
全部 582/582 通过（累计 6 绿 1 红）。

最可能的嫌疑是那两条新加的队列桩用例（`a_cookie_download_goes_into_the_queue_with_its_cookie`、
`a_direct_download_says_why_it_is_not_in_the_window`）：它们起一个本机 HTTP 桩，
而 `try_queue` 的客户端超时是 5 秒。机器忙到桩线程 5 秒内没应答，`try_queue` 就会返回
`TimedOut`，回复变成 `{"op":"error","message":"队列响应超时"}`，断言 `mode == "queue"`
随之失败 —— 这正是之前那条**旧**用例红灯时的报错形状（"队列响应超时，未重复下载"）。

没有当场改超时（那是生产代码里的取舍，不该为测试放宽）。留待下次复现时确认：
如果又红，先看报错是不是 `队列响应超时`；若是，就把这两条用例改成
"桩起好之后再发请求"的连接确认式等待，而不是靠 5 秒上限兜着。
