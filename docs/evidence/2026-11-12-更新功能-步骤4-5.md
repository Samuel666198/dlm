## 一、新增了什么

| 位置 | 内容 |
|---|---|
| `src/updater.rs`（新） | 更新器的**可测部分**：下载、校验、解压、替换+回滚、扩展落地、`installed.json` |
| `src/bin/dlm-updater.rs`（新） | 独立更新进程：等 GUI 退出 → 下载 → 校验 → 解压 → 替换 → 装扩展 → 写标记 → 重启 |
| `gui::spawn_updater` | 「立即更新」：把 updater 拷到临时目录再起，然后 GUI 自己退出 |
| `gui::UpdateView` | 加 `extension_disk`（磁盘上的扩展版本），与 `extension_running`（浏览器里跑的）对照 |
| `gui::app::update_ui` | 「立即更新」按钮（仅 `installable` 时可用）、扩展状态一句话、复制 `chrome://extensions`、打开扩展目录 |
| `packaging/*.ps1` | 打包与安装的 exe 清单加 `dlm-updater.exe`；打包时校验 `gui::RELEASE` 与 `-Release` 一致 |

### 更新流程（和设计文档一致，但把「为什么」写在了代码里）

```
dlm-gui 发现新版 → 用户点「立即更新」
  ├─ 把 dlm-updater.exe 拷到 %TEMP%\<ts>\  （这样安装目录里的那份可以被替换）
  ├─ 起 updater：--url --sha256 --install-dir --extension-dir --data-dir
  │              --release --core --extension --wait-pid <GUI 的 pid> --restart <GUI exe> --log
  └─ GUI 退出
updater：等 pid 退出 → 下载 → 校验 sha256 → 解压 → 换四个 exe → 装扩展 → 写 installed.json → 重启 GUI
```

`--wait-pid` 用的是 `OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject`，阻塞等待，
不轮询 `tasklist`、不启子进程、不占 CPU。

### 退出码（失败也要能读懂）

| 码 | 含义 | 后续动作 |
|---|---|---|
| 0 | 完成 | — |
| 2 | 参数不对 | 什么都没动 |
| 3 | sha256 不符 | **一个文件都不动** |
| 4 | 替换失败 | 已回滚，并把旧 GUI 拉起来 |
| 5 | 下载失败 | 同上 |
| 6 | 解压失败 | 同上 |
| 7 | 扩展落地失败 | 同上（exe 已经换了，但扩展没换） |
| 8 | 写标记失败 | 同上 |

**失败的共同善后**：只要给了 `--restart`，就把旧 GUI 拉起来。用户点了「立即更新」，
结果是程序消失、什么都没发生 —— 那比不更新更糟。

## 二、两个当场撞出来的坑（都写进了代码注释）

### 坑 1：`Expand-Archive -Force` 在这台机器上根本跑不通

实测报错：

```
Expand-Archive : Cannot find an overload for "ExtractToDirectory" and the argument count: "3".
```

Windows PowerShell **5.1**（就是 `powershell.exe`）会走进三参数的 `ExtractToDirectory(src, dest, true)`，
而 .NET Framework 里没有那个重载。加不加 `-Force`、目标目录建没建，两条路都试过，都报同一句。

修法：直接调两参数的 `[System.IO.Compression.ZipFile]::ExtractToDirectory`，
`Add-Type -AssemblyName System.IO.Compression.FileSystem` 之后调用 —— 5.1 与 pwsh 7 实测都通。

> 这条不是「写法不优雅」，是**在目标机器上不可用**。没有那条真打的 zip 用例
> （`a_real_zip_roundtrips_through_expand_archive`）根本发现不了，因为单元测试里没人真解压。

### 坑 2：`.ps1` 文件必须带 UTF-8 BOM，否则 PS 5.1 读成乱码后连语法都错

用 `Set-Content -NoNewline`（PowerShell 7，默认 utf8 **无** BOM）改过 `build-package.ps1` 之后：

```
L91: The string is missing the terminator: '.
```

原因：PS 5.1 对无 BOM 的文件按**本地代码页**解码，中文注释变成乱码
（`鏇存柊娓呭崟璺熷寘…`），乱码里的字节把引号配平搞坏了。

修法：`packaging/*.ps1` 与 `gates.ps1` 统一存成 **UTF-8 with BOM**。
用 pwsh 7 的 `Parser::ParseFile` 查不出来（它按 UTF-8 读，报 `no errors`），
**必须用 `powershell`（5.1）验**。

## 三、端到端演练（真进程、真 HTTP、真解压）

一次性探针（`tmp/e2e-updater.ps1` + `tmp/serve-zip.mjs`，跑完即删）：
造一个假安装目录（三个 exe 是占位内容、扩展是 0.2.12）、打一个真 zip、用 node 起本地 HTTP，
然后跑真的 `dlm-updater.exe`。

```
zip=992 B sha256=a3958b612f7d04947d518ae74ba9bbb360de0478e533554aef5d50c5c44866fa

正臂（正常更新）：exit 0
  PASS dlm.exe / gui / host / updater 四个都换成 NEW-*
  PASS 没有留下任何 *.dlm-old
  PASS 扩展落到磁盘、旧的 background-0.2.12.js 被清掉、新的 0.2.99 就位
  PASS installed.json = {release 1.0.0, core 0.1.1, extension 0.2.99}
  PASS 日志里有「更新完成」
负臂（sha256 全 0）：
  PASS exit 3，diag 里带着算得的真摘要
  PASS 一个文件都没动，installed.json 也没重写
重启：
  PASS exit 0，日志里有「重新启动」→ 子进程真的被 spawn（拿真 dlm.exe 当靶子）
E2E PASSED（20 项）
```

## 四、门禁（实测）

```
fmt PASS · lib 374 passed（361 → 374，+13）· bins 4 · integration 121
clippy -D warnings PASS · extension PASS（version=0.2.12）
GATES PASSED
```

新增 13 条单测的判据名：

| 用例 | 钉住什么 |
|---|---|
| `installed_state_roundtrips_and_a_broken_file_is_the_same_as_none` | `installed.json` 坏了不许让程序起不来 |
| `the_local_release_comes_from_the_installed_marker_not_the_compile_time_constant` | 装过一次更新后，「本机版本」来自标记文件 |
| `verify_file_names_both_digests_and_never_passes_an_empty_expectation` | 空摘要永不放行（复用 engine 的判据） |
| `swap_replaces_every_binary_and_leaves_no_backup_behind` | 换完不留 `.dlm-old` |
| `swap_refuses_before_touching_anything_when_the_package_is_incomplete` | 缺一个文件就一个都不换 |
| `a_failed_swap_rolls_the_already_replaced_files_back` | 换到一半失败 ⇒ 已换的回到旧内容 |
| `install_extension_copies_files_and_drops_the_previous_service_worker` | 旧 `background-<版本>.js` 要清掉 |
| `install_extension_refuses_a_package_without_the_extension` | 包里没扩展就不装 |
| `a_real_zip_roundtrips_through_expand_archive` | 真打 zip 真解压（坑 1 的针） |
| `the_extension_line_names_all_three_versions_when_they_disagree` | 「磁盘 / 浏览器 / 清单」三个版本一起说 |
| `a_reloaded_extension_needs_no_action` | 重载过就不再催 |
| `an_uninstalled_extension_says_the_package_carries_a_newer_one` | 还没装时说「包里带的是新版」 |
| `no_extension_information_renders_nothing` | 什么都不知道就不刷一行废话 |

## 五、还没验证到的（诚实清单）

| 事 | 为什么没验 | 什么时候能验 |
|---|---|---|
| **真人点「立即更新」走完整条路** | 需要 GUI 交互（egui 的按钮点不了 headless），E2E 验的是 updater 那一侧 | 发一个真版本之后 |
| **对已发布版本的自我更新** | 已发布的 `v0.1.0` 是**没有 updater 的旧包**；更新它的新版还没发 | 发 `v0.1.1` 时顺带验 |
| **扩展「请重载」提示的完整闭环** | 需要用户在浏览器里真的点「重新加载」，扩展才会报新版本 | 用户点完就看得到 |
| **重打 0.1.0 包** | `target\package\dlm-0.1.0-win-x64\` 里有个正在运行的 `dlm-gui.exe`（pid 12204）占着暂存目录，删不掉；而且重打会换掉本地那份与已发布 `v0.1.0` **同 sha 的 zip** | 发 `v0.1.1` 时按新版本号重打 |

> 打包链路本身本轮验到了两处：`cargo build --release --bins` 确实产出
> `target\release\dlm-updater.exe`（4,529,152 B），打包/安装脚本的 exe 清单都已含它；
> `-Release` 与 `gui::RELEASE` 不一致会被脚本 `throw`（实测）。

### 发新版本时的两条硬规矩

1. **`gui::RELEASE` 必须与 `-Release` 一致**。打包脚本现在会拦（实测：`-Release 0.1.1`
   而常量还是 `0.1.0` ⇒ 直接 `throw`）。不拦的话，从源码装的人会永远被提示「有新版」。
2. **先传 Release 资产，再改 `main` 的 `latest.json`**（硬纪律第 6 条，原样适用）。

顺序建议：改 `RELEASE` → 跑门禁 → `build-package.ps1 -Release X -Notes …`（顺手产 `latest.json`）
→ 建 Release 传包 → 用脚本产出的 `latest.json` 覆盖 `main` 的那份 → 推 `main`。
