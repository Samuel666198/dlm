# dlm 发布通道

这个分支**只放发布物**，不放源码。

| 文件 | 用途 |
|---|---|
| `latest.json` | 更新清单。桌面端从这里读版本号、下载地址、sha256 |

源码在 [`sdd/dlm-kernel`](https://github.com/Samuel666198/dlm/tree/sdd/dlm-kernel) 分支。

## 为什么单独一个分支

更新清单一旦发出去，旧版本的更新器就会一直来读它。挂在开发分支上有两个隐患：

1. **分支名不稳** —— 以后改名或合并，已经发出去的更新器全断
2. **开发分支上乱写会直接影响所有用户** —— 任何一次 push 都可能改掉清单

所以开发分支随便折腾，这个分支只在真正发版时更新。

## latest.json 字段

```json
{
  "release": "1.0.0",
  "core": "0.1.0",
  "extension": "0.2.12",
  "url": "https://.../dlm-1.0.0-win-x64.zip",
  "sha256": "...",
  "size": 9437323,
  "notes": "更新说明",
  "min_core": "0.1.0",
  "published_at": "2026-11-12T18:00:00Z"
}
```

- `release`：用户感知的软件版本，更新器据此判断要不要更新
- `core`：桌面端三个 exe 的版本，与 `Cargo.toml` 一致
- `extension`：扩展版本，与 `manifest.json` 一致
- `sha256`：**必须**。要装进安装目录的东西，不校验等于任意代码执行
- `min_core`：低于这个内核版本不支持自动更新

### 三个版本号的分工

用户感知的是 `release`（"这个软件更新了"），不是 `core` 从 0.1.0 变 0.1.1。
`core` 与 `extension` 是内部实现细节，用来告诉用户"这次更新会不会连带换扩展"。

### 扩展不会自动更新

扩展是「加载已解压」方式装的，浏览器**不允许**程序化替换。所以联动更新只能做到：

1. 桌面端把新扩展文件写到 `%LOCALAPPDATA%\dlm\extension`
2. 提示用户"请到 chrome://extensions 点重新加载"
3. 扩展通过 Native Messaging 上报自己正在跑的版本
4. 桌面端比对磁盘版本与运行版本，确认用户真的重载了

做不到"点一下就换掉扩展" —— 这是浏览器限制，不是实现问题。

## 发布流程

1. 在开发分支上改代码、跑门禁（`gates.ps1` 全绿）
2. `packaging/build-package.ps1` 出 zip，记下 sha256 与字节数
3. 在 GitHub 建 Release，tag `v<release>`，上传 zip
4. 更新本分支的 `latest.json`
5. 推本分支

第 4 步必须**在 Release 上传成功之后**做 —— 清单先发出去而包还没上传，用户点了更新会 404。
